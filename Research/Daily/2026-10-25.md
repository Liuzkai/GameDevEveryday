### ✅ 新建概念 [[Overdraw]]（第 44 个）

**它回答的不是"什么是 overdraw"，而是"哪一层被收钱"**：

**① 三种口径，数值可以差一倍以上。** Coverage（落在像素上的片元数）/ Shaded（真正跑完片元着色器的）/ Blended（参与 ROP 混合的）。不透明物体被 early-Z 或 HSR 剔掉后，**Coverage 很高但 Shaded ≈ 1**。所以"我们这帧 overdraw 是 8×"这句话，**不说是哪个口径就等于没说**。

**② 成本恒等式：`层数 × 屏占比 × 单价`。** 三个乘数可独立调节，而且性质不同——**层数是场景属性**（美术叠了几层），**单价是技术属性**（shader 多贵、要不要排序）。**两者混在一起谈，就会出现"这个特效粒子不多但很卡"的争论**。

**③ 一张换算表，把"粒子数"翻成"像素账"**（1080p）：

| Sprite 尺寸 | 单粒子占全屏 | 铺满 1× 全屏需要 | 100 个的总屏占比 |
|---|---|---|---|
| 64 × 64 | 0.20% | 506 个 | **0.20×** |
| 128 × 128 | 0.79% | 127 个 | 0.79× |
| 256 × 256 | 3.16% | 32 个 | **3.16×** |
| 512 × 512 | 12.6% | 8 个 | 12.6× |

**"同屏 100 个粒子"这句话，在 64² 与 256² 之间相差 16 倍填充。**

### 🔧 对你那张 SABC 表的具体修订建议

现行表有一行「**同屏粒子数**：S 3000 / A 1200 / B 400 / C 100」。

**这一行单独存在时没有性能含义。** 按上表换算，同一个 3000：

| 假设平均 sprite 尺寸 | S 档 3000 粒子的屏占比 |
|---|---|
| 64² | **5.9× 全屏** |
| 128² | **23.7× 全屏** |
| 256² | **94.8× 全屏** |

这就是 [[Reeves — Particle Systems (1983)]] 法则 ①（"数量随屏占比"）在 1983 年就说过的事，而预算表把它丢掉了。

**建议（不改分级、只改度量）**：

$$
\text{像素预算} \;=\; \sum_i A_i \;\le\; k \times A_{\text{screen}}, \qquad k = \text{档位系数}
$$

- S / A / B / C 各给一个 $k$（例如 8× / 3× / 1× / 0.3×）；
- **粒子数上限保留，但降级为辅助约束**——它管的是 CPU 侧 spawn/更新与 draw call，**不是填充**；
- 好处很实在：**美术能自己换算**——"要把粒子从 128² 做到 256²，数量就得砍到 1/4"，这是一条能当场执行的规则，而不是一句"省着点用"。

### ✅ 新建概念 [[GPU Architecture]]（第 45 个）

**写成一张成本地图**，而不是架构百科：

- **三类资源**：算力 / 带宽 / 延迟隐藏（occupancy 只是"延迟隐藏的库存"，不是目的）；
- **存储层级**四个量级（寄存器 → shared/L1 → L2 → VRAM），**这是"移动端先降分辨率、PC 先降 shader"的物理原因**；
- **固定功能单元表**：光栅化器（quad 2×2 粒度）/ ROP（**吞吐与分辨率直接绑定**）/ 纹理单元 / 前端；
- **六个实测指标的归属表**：Particles → compute；DrawCalls → 前端+驱动；Primitives → 光栅化器；OverDraw → ROP+带宽；CPUTime → 提交线程；GPUTime → 全部。

**一条可直接用的判据**：**先看 `CPUTime : GPUTime` 的比值，再动手删特效**。CPU 高 GPU 低 = 提交问题（合批/并行提交）；GPU 高 = 像素或几何问题；两者都高才是内容超载。**不看比值就开始优化，通常优化的是错的那一半。**

## Classical Research

### ✅ [[Everitt — Interactive Order-Independent Transparency (2001)|Cass Everitt 2001 — Interactive Order-Independent Transparency]]（A 经典·历史重要性 4）

**证据形态先说清楚**：这是 NVIDIA 的 **14 页技术演示文稿**，不是同行评审论文，**全文没有任何计时数据**。它的地位来自"第一次把 OIT 的成本写成一句话"，不来自实验。

**历史角色**：2001 年的硬件只有"深度测试 + 混合"两个阶段，**没有任何 per-pixel 排序能力**。正确半透明只能靠应用把多边形排好序——而多边形会相交、场景会动、排序维护成本全压在应用侧。于是行业默认两条路：**逐图元排序（近似对）** 或 **加法混合（对就不对了）**。

**它给出的第三条路**：**用层号当排序。**

```text
第 0 遍：正常深度测试 → 拿到最近片元（第 0 层）
第 i 遍：把第 i-1 遍的深度当只读纹理，深度测试改成 GREATER
        → 这一遍画出来的，恰好是「比上一层更远的最近片元」（第 i 层）
两个深度缓冲 ping-pong，每遍存一张 layer 纹理，最后从后往前合成
```

**整套机制里没有一个数据结构，只有一个比较方向。** `GREATER` 测试就是 `argmin{ depth(p) : depth(p) > depth_{i-1}(p) }` 的硬件实现——**遮挡关系被翻译成前后两次遍历的顺序关系**。

**成本，一句话**：**`层数 × 一遍场景`**。片元数逐层下降（图 2 到第 3 层只剩零星碎片），但**几何遍历不降**——顶点、图元装配、光栅化全部重跑 n 次。**这是"顶点密集场景最吃亏"的原因。**

**当年最聪明的一手是"借"**：2001 年没有双深度缓冲扩展，但**只读深度测试正好是 shadow map 的能力**，而且深度测试的相机可以是任意位置。于是一份深度走普通深度缓冲（可写），另一份当阴影贴图纹理（只读），再用 `DEPTH_REPLACE` 纹理着色器解决两条路径的精度不变性。**新能力常常不是等来的，是从邻近阶段借来的。**

**唯一"定量"的东西要打折看**：作者说 **"n = 4 is often quite satisfactory"**（图 4：1 层基本错、2 层有内部、3 层接近、4 层几乎无差别）。**这是单场景目测，没有误差度量，没有计时。**

**四代演进，其实在换同一个变量——"顺序外包给谁"**：

| 年份 | 方案 | 顺序外包给 |
|---|---|---|
| 1984 | Carpenter A-buffer | 每像素链表（软件） |
| **2001** | **Everitt depth peeling** | **像素层号（n 遍场景）** |
| 2008 | Bavoil & Myers 双面剥离 | 像素层号（前后同时） |
| 2010 | Stochastic transparency | 随机采样 |
| 2013 | Weighted Blended OIT | 权重（放弃精确顺序） |
| 2023+ | 3DGS 排序键 | 排序键（层数爆炸） |

## Technology Evolution

```text
overdraw 的"计价单位"一直在换（1990s–2026）

fill rate（Mpx/s）        1990s：像素吞吐是规格表第一行
      ↓ 可编程着色
每片元算法复杂度          2000s：overdraw 从"像素数"变成"每像素算多少"
      ↓ deferred shading
G-buffer 写入次数         2000s 中后期：着色挪到每像素一次，但写入本身仍是 overdraw
      ↓ 移动 TBDR
tile 内存 + flush 次数     2007+：HSR 让不透明近乎免费，代价转到片上容量
      ↓ 图元变成半透明层
层数                      2023+：3DGS 每像素几十~几百层，overdraw 回到舞台中心
```

**同一条线，换个角度看"顺序"**：

```text
1984  A-buffer        每像素存一列片元（软件，正确，慢）
2001  depth peeling   层号 = 排序（n 遍场景）
2008  dual peeling    前后同时剥（≈2×）
2010  stochastic      用随机换排序（噪声换成本）
2013  WBOIT           用权重换顺序（一遍、近似）
2023+ GS 排序键        用键换顺序（层数爆炸后的调度问题）
```

**两条线的交点**：**"顺序"和"填充"从来是同一个预算的两面**——你要么为层数付几何，要么为噪声付采样，要么为近似付画质。

## Important Relationships

- **[[Overdraw]] ↔ [[Real-Time VFX Performance Budgeting]]**：**同一件事的两个视角**。前者是"账怎么算"（层数 × 屏占比 × 单价），后者是"钱怎么分"（SABC × 五档画质）。**今天的结论是：你的分钱表缺一个和"面积"挂钩的科目**；
- **[[Overdraw]] ↔ [[Tile-Based Rendering]]**：**同一个词在两套架构上是两种成本**。PC 上是 ROP 带宽（8 B/片元），移动端是 tile 内存与 flush 次数。**"跨平台用同一个 overdraw 阈值"是错的**；
- **[[Overdraw]] ↔ [[Gaussian Splatting]]**：GS 把"层数"推到几十~几百，于是排序键、tile binning、随机光栅化全成了必需——**它是 overdraw 这条线在 2023 年后的极端样本**；
- **[[Everitt — Interactive Order-Independent Transparency (2001)|Everitt 2001]] ↔ [[Reeves — Particle Systems (1983)]]**：**同一个约束的两次解法**。Reeves 用加法混合**删掉顺序**（换来确定性、免排序），Everitt 用层号**买回顺序**（换来正确性、付出 n 遍几何）。**加法混合的便宜不是免费的，它把"吸收/遮挡"卖掉了**；
- **[[GPU Architecture]] ↔ 你的六个指标**：**不是"底层知识"，是归因表**。CPUTime 高而 GPUTime 低，说明问题在提交线程——这时候优化 shader 是白干。

## Key Takeaways

**1. "数"和"账"是两件事，今天补的是账。** 同屏粒子数是一个**数**，overdraw 才是**账**。数合规不等于账合规——3000 个 64² 和 3000 个 256²，账差 16 倍，而"数量"这个数一模一样。**评审时如果只审数量，审的其实是一个和性能弱相关的代理指标。**

**2. 口径先于数字。** Coverage / Shaded / Blended 三种口径，混用会得出矛盾结论。这条不只适用于 overdraw——**任何跨工具、跨平台的性能数字，先问"这个数是怎么量的"**。本周三篇论文（RLSplat / KoalaGS / AnyGameRenderer）都在做同一件事，只是它们在论文里做，你在项目里做。

**3. 单价取决于管线阶段，所以"统一阈值"必然错。** 同样是 10× overdraw：不透明几何靠 early-Z 近乎免费，alpha test 半价，半透明全价，带 distortion 的再翻一倍。**"我们规定所有特效 overdraw ≤ 4×"这种规则，本质是在用一个数字管四种不同的成本。**

**4. 精确顺序的代价可以写成一句话：`层数 × 一遍场景`。** Everitt 2001 给的不是"更好的透明"，是**把排序这件事变成可数的层**——一旦可数，就能定价。加法混合之所以便宜，是因为它把"顺序"这个维度整个删掉了；它卖掉的正是**吸收与遮挡**。

**5. 补洞比加页划算。** 两个空洞概念一补，11 处引用同时变实，六篇旧笔记的"前置"从占位变成可读。**这周的图谱工作应该继续按这个逻辑走**：先清高频空洞（`Temporal Stability` / `Artistic Intent Preservation` / `Motion Tokenization` 各 4 处），再考虑开新线。

**6. 今天没有前沿论文，但今天不空。** 规则里"允许报告无高价值前沿"这一条，本质是在保护**不被配额绑架的判断力**。一周之内第三次薄批/空批，说明的是**这个领域的提交节律**，不是"研究变少了"——10 月中那批（MG4.0 / RLSplat / AnyGameRenderer / Kaushik）密度仍然很高，只是被消化完了。
