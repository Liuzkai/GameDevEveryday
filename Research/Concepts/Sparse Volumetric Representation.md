# Sparse Volumetric Representation

## Definition

**只在"有内容的地方"存值的三维标量场表示。** 不是一种格式，是一族结构——它们共同的赌注是：

> **域可以无限大，但真正有值的体素永远只占极小一部分。**

这个赌注在游戏与 VFX 里几乎总是成立：烟、火、云、爆炸、SDF 碰撞体、破坏碎片的内部距离场，全都是"薄薄一层壳 + 大片空白"。一个 7897×1504×5774 的包围盒里，龙的表面积只占 **0.04%**——稠密表示要 1/4 TB，稀疏表示要 1 GB。

**所以这一页讲的不是"怎么存体积"，是"稀疏这件事要付什么代价、换什么能力"。**

## Core Principle

任何稀疏体表示都必须回答三个问题，而**三个答案互相打架**：

| 问题 | 直觉答案 | 代价 |
|---|---|---|
| ① 坐标怎么映射到存储？ | 树 / 哈希 / 压缩行 | 树 → 跳数；哈希 → 丢相干性；压缩行 → 只能按序 |
| ② 拓扑和值分开存吗？ | 分开更省 | 多一层间接；换来"换一套数据不换结构" |
| ③ 拓扑能改吗？改了多贵？ | 当然能 | 逐体素改 ⇒ 锁 + 堆 + 随机访存 |

**这三问答完，一个结构的全部能力边界就定了。**

### 判据一：稀疏度与跳数是一对直接交换

树形结构的关键指标不是"是不是树"，是：

$$\text{访问成本}\ \approx\ \text{跳数}\ \times\ \text{每跳的固定开销}\ -\ \text{缓存命中省下的部分}$$

八叉树每层分 2 叉：262144³ 的域要 18 层，**一次访问 18 次指针跳**，每次只覆盖 2 个体素。
VDB 用 `[6,5,4,3]`：4 层，**一次跳覆盖 4096 个体素**。

> **"跳的成本"必须被"每跳覆盖的体素数"摊薄。** 这是"浅而宽"胜过"深而窄"的全部算术。

但宽有宽的代价：每层的直接访问表（DAT）大小是 $2^{3\cdot LOG2DIM}$。把树压到 2 层（`[10,3]`）会让顶层 DAT 变成 $1024^3$ 个槽——**和 4 层配置同样的可用分辨率，内存差几个数量级**。

**所以"最优树深"不是调参，是一道有解的优化题：跳数 × 每跳开销 × DAT 内存，三者对树深的方向相反。**

### 判据二：把"存在性"抽出来单独存，其余操作全部降级

这是 VDB 里最漂亮的一步。每层节点带两张位掩码：`childMask`（哪些子节点存在）+ `valueMask`（哪些体素是 active）。这两张 1 bit/体素/层的表同时干五件事：

1. **拓扑编码** —— "存在吗"就是这 1 bit；
2. **顺序迭代** —— 遍历活跃体素 = 遍历置位；
3. **无损压缩** —— 答案是"否"就不用存值（叶节点缓冲可以裁到只剩 active）；
4. **布尔运算** —— CSG 的并/交/差 = 位与/位或，**整块做**；
5. **形态学** —— dilation / erosion 也是位运算。

> **一旦"存在性"被单独抽出来，所有涉及它的操作都从"改数据"变成"改位图"，而位图可以整块处理。**

这条判据可以搬到任何地方：occupancy 位图、dirty flag 表、LOD 选择表、可见性掩码——**只要是"某个格子上有没有东西"，就把它压成 bit，然后把算法改成对整个 bit 串做运算。**

### 判据三：拓扑能不能改，取决于"改"是逐体素还是批量

这是 2013 与 2026 之间那条最重要的分界线。

| | 逐体素（OpenVDB） | 批量同步（2026） |
|---|---|---|
| 语义 | 任何时刻可增删任一格 | 每轮整体重写一次（epoch） |
| 线程安全 | ❌（要外部加锁/约定） | ✅（先算后建，天然并行） |
| 内存 | 只需一份 | **需同时持"改前/改后"两份** |
| GPU | 不友好（分配是串行的） | 友好（前缀和 + 单块分配） |
| 适合 | 交互式雕刻、逐帧稀疏编辑 | 模拟、重建、体素化 |

**"批量同步"不是性能优化，是把"改"从状态机变成函数。** 一旦它是个函数，"先算出结果集合，再一次性建出来"就成立，位并行才有地方落脚。

### 判据四：只读不是结构的天性

NanoVDB（2021）为了 GPU 的线性布局**放弃了拓扑可变**；五年后同一批人（含原作者 Museth）证明：

> `static topology is not an inherent trait of the NanoVDB data structure, but rather a limitation of the algorithms previously used to maintain it.`

**每一次"为了快而砍掉的能力"，都会在若干年后以"保留快路径的旁路"形式补回来。** 补回来的代价总是两样：**多一条代码路径** + **一个必须维持的不变式**（VBM 那两条：无空叶、跨叶索引连续）。

## 四代谱系（这张表是这一页的骨架）

| | **OpenVDB** 2013 | **NanoVDB** 2021 | **Index-Grid** 2024 | **Dynamic GPU** 2026 |
|---|---|---|---|---|
| 存储稀疏度 | 中 | 中 | **高** | **高** |
| 内存布局 | 碎片（指针+堆） | **线性** | **线性** | **线性** |
| 拓扑 / 数据分离 | 否 | 否 | **是** | **是** |
| 随机访问 | 读写 | **只读** | **只读** | **只读** |
| 拓扑适应 | **动态（体素粒度）** | 静态（需重建） | 静态（需重建） | **动态（批量同步）** |
| 顺序访问 | 否（accessor） | 否（accessor） | 否（accessor） | **是（SIMD/SIMT）** |
| 平台 | 仅 CPU | CPU + GPU | CPU + GPU | CPU + GPU |
| 定位 | 通用、最大灵活性 | 光线追踪 / 静态隐式面 | 静态拓扑 + ML 负载 | 动态数据的通用最优 |

**读这张表的正确方式：每一代都只改一列，而每一列的改动都是"用一列换另一列"。**

- 2013 → 2021：**用"可改"换"线性布局"**（碎片→线性，动态→静态）；
- 2021 → 2024：**用"多一层间接"换"稀疏度"**（拓扑/数据分离，<2 bit/体素）；
- 2024 → 2026：**把"可改"补回来，且不还回线性布局**——代价是"批量同步"这个新约束。

## Prerequisites

- **树结构与 B+ 树**：分支因子、深度、节点大小三者的关系。VDB 的核心类比不是八叉树，是**文件系统里的 B+ 树**（浅、宽、固定深度）。
- **CPU 缓存层级**：L1/L2/L3 的大小与延迟梯度。**VDB 的节点尺寸是照着这个梯度设计的**（leaf ≈ L1，internal ≈ L2/L3，root ≈ 主存）。见 [[GPU Architecture]]（该页讲的是 GPU 的对应物：显存带宽是硬下界，warp 空转是稀疏算法的敌人）。
- **位运算**：popcount、位与/或、位移。**不理解 popcount 就看不懂"为什么 1 bit 能当索引用"。**
- **窄带 level set**：见 [[Fluid Simulation]]——"只在零等值面附近 ±3 体素存距离值"是这一切的应用前提。

## Historical Evolution

```text
1980s   八叉树进入渲染与建模
2000s   自适应距离场 / brickmap / N³-tree / GigaVoxels
          —— 都在解决"稀疏"，没人同时解决"能改 + 能随机访问"
2006    DT-Grid（CRS 的 3D 类比）/ H-RLE（RLE 逐轴）
          —— 最省内存的那条路，但只能按序访问
2013 ★  VDB：浅宽 B+ 树 + 每节点位掩码 + accessor 反向遍历
          —— 稀疏 / 随机访问 / 动态拓扑三者首次兼得（CPU）
2014    HDDA：树本身成为光线加速结构
2021    NanoVDB：线性化 + 相对寻址 ⇒ GPU；用"只读"换速度
2024    Index-Grid / fVDB：拓扑与数据分离，<2 bit/体素；仍只读
2026 ★  Sifakis et al.：位并行批量拓扑算子 + VBM 顺序访问
          —— 把"可改"补回来，不放弃线性布局
```

**一条贯穿十三年的主线：每一代都在减少"一次间接寻址"。** 浅宽（少跳）→ 线性（跳变算）→ 分离（一跳服务多份数据）→ 批量（跳彻底消失）。

## Important Papers

- [[Museth 2013 — VDB High-Resolution Sparse Volumes with Dynamic Topology|Museth 2013（VDB）]] — **本页的锚点。** 定义了全部术语（root / internal / leaf / childMask / valueMask / tile value / accessor）与全部取舍（<2× 内存换 4–100× 算力）。
- [[2026-11-10-Sifakis — Dynamic GPU Sparse Grids and Voxel-sequential Processing in NanoVDB|Sifakis et al. 2026]] — **把 2013 标题里的 "with Dynamic Topology" 在 GPU 上补完**：批量同步拓扑 + VBM 顺序访问。
- （库外）NanoVDB（Museth 2021, TOG）—— 线性化那一步，本页所有"只读"的来源。
- （库外）Index-Grid / fVDB（Williams et al. 2024）—— 拓扑/数据分离。
- （库外）DT-Grid（Nielsen & Museth 2006）/ H-RLE（Houston et al. 2006）—— 内存这条轴上的对手，用来量"VDB 多花的那 2 倍买了什么"。

## Related Concepts

- [[Fluid Simulation]] — **主应用**。窄带的四步循环（dilate → advect → reinit → prune）前三步完全依赖这一页的拓扑能力。见今日回填。
- [[Participating Media]] — **下游消费者**。体积渲染读的就是这种网格；HDDA 让"直接遍历稀疏树"成为渲染路径。
- [[GPU Architecture]] — **约束来源**。这一页的所有"为什么快"最终都落在两条上：跳数（延迟）与是否碰字节（带宽）。
- [[Streaming]] — **同一个动机的另一种实现**。资源流式靠"按需加载"躲随机访存；VBM 靠"把随机访问改成顺序访问"躲它。**两者都在把"随机"变成"顺序"。**
- [[Budget Units]] — **计价单位的选择**。VDB 与 DT-Grid 的比较是"用 2 倍内存买 100 倍算力"；选错计价单位就会得出相反结论。

## Technologies

- **OpenVDB**（ASF 开源，2012 起）：DCC 的事实标准体积格式。Houdini（Pyro / Vellum / MPM 的缓存）、Blender Cycles、Arnold、V-Ray、RenderMan 都基于它。
- **NanoVDB**：GPU 侧子集，线性布局，只读。用于实时渲染与光线追踪。
- **fVDB / Index-Grid**：PyTorch 生态的 GPU 稀疏体框架，拓扑/数据分离，面向稀疏 ML 与重建。
- **HDDA**（Hierarchical Digital Differential Analyzer）：在 VDB 树上直接做光线步进，不必转稠密。
- **窄带 level set（TSDF / SDF）**：最典型的载荷形态——只存零等值面附近的值。

## Game Applications

| 场景 | 用哪种 | 为什么 |
|---|---|---|
| **Houdini 烟/火/云缓存** | OpenVDB | 就是它；分辨率、叶节点大小、tile value 直接决定缓存体积与重算范围 |
| **实时烟火 / 体积雾** | NanoVDB（或自建稀疏网格） | 需要 GPU 上每帧读；拓扑预先烘焙 |
| **SDF 碰撞体 / 软体** | 窄带 SDF | 距离场做碰撞查询是 O(1)；比三角网格便宜 |
| **破坏预处理** | 体素化 + UDF | 每个碎片生成内部距离场，运行时查"这个点还在不在" |
| **体素 GI / 探针** | 稀疏占据网格 | 空区域用一个 tile value 代替 |
| **方块体素地形（Minecraft 类）** | ❌ **不要用这套** | 那是 dense chunk + 面剔除；稠密才是对的 |

**判据：内容是不是"薄壳 + 大片空白"？** 是 → 稀疏体；否（如方块地形、均匀填充的体积雾）→ 稠密分块。

## Learning Gap

**库内此前 14 处提 voxel、0 处讲"体数据是怎么存的"**——这一页补的是这个洞。但补完之后暴露出三个真缺口：

1. **"分辨率该定多少"没有判据。** 8³ 叶节点是默认，但**什么时候该用 16³ / 4³**？论文只说 `[6,5,4,3]` 综合最好，没给"按载荷类型选配置"的规则。**这是最实用的一个缺口**：Houdini 里改缓存精度时，你其实在改叶节点与树的组合。
2. **稀疏体在游戏运行时里的真实带宽账没有。** 论文给的是工作站 / 服务器 GPU 的批处理数字；**游戏是每帧 16.6 ms 的总预算**，且要与渲染抢带宽。**没有一篇给"一帧的烟雾模拟能吃多少 GB/s"。**
3. **体素 GI 与稀疏体的交界没人写。** 稀疏体表示天然适合"空区域几乎免费"，而体素 GI 的核心问题恰好是"哪里有几何"——两者该共用一份 occupancy，但库内没有材料。

## Next Step

**按需，不急。** 若要动手，最小闭环是：

1. 打开一个手上的 `.vdb` 缓存（Houdini 的烟或云），记录三个数：**分辨率、活跃体素数、文件大小**；
2. 算一次**稀疏率** = 活跃体素 / 包围盒体素。低于 1% 时，你就在用稀疏结构的甜区；高于 20% 时，稀疏结构可能已经不划算了；
3. 把分辨率降一半重烘一次，看**文件大小是否按 8 倍缩**——**不按 8 倍缩，说明你的内存被"叶节点粒度"而不是"体素数"主导**（8³ 的叶在低占用时浪费 99%）。

**这三步加起来 20 分钟，但它能让你在下次"要不要提高模拟精度"的争论里给出一个数，而不是一个感觉。**
