# Streaming

## Definition

**流式 = 让工作集大于任何一层存储，仍然把系统跑下去。**

标准配置是一条**层级**（tier）：快而小 → 慢而大，块在层之间搬。所以流式的本质不是"加载得快"，而是：

> **把"装不下"这个容量问题，换成一串"来不来得及"的时间问题。**

这个交换不是免费的，它只在两个条件同时成立时划算（见 Core Principle）。**这两个条件就是流式的全部判据**——它们比任何实现细节都重要，因为它们决定"这条路能不能走"，而实现只决定"走得多好"。

**先分清三件常被混为一谈的事**：

| 手段 | 改的是什么 | 容量墙能推多远 |
|---|---|---|
| **压缩 / 量化** | 每块多大（$B_c$） | **常数倍**（2 bit 就是 2 bit） |
| **流式 / 分层** | 块放在哪 | **没有上限**（只要愿意付盘的空间） |
| **重算** | 块要不要存在 | 无上限，但**把容量换成了算力** |

**这三者的先后顺序经常被搞反**：先量化、再流式，是最常见的顺序；但**量化只买常数倍，它推不远**，真正解决问题的那一步一定是"搬家"或"重算"。

## Core Principle

### 两个条件（缺一不可）

**① 访问集可先验。** 下一步要哪些块，必须在**算之前**知道，或者至少能高置信度预测。

- 操作系统做不到这件事：**未来的页引用串是未知的**，所以它只能靠历史（LRU）猜；
- 但**很多游戏负载是可以的**：玩家位姿是输入（世界模型、地形、植被）、技能时序是配置（VFX）、关卡流送点是设计（Level Streaming）。
- 一旦可先验，预取就从"投机"变成"计算"。

**② 搬运可隐藏。** 搬一块的时间必须小于算一块的时间窗口 $T_c$：

$$\text{零停顿条件}:\quad \frac{r_{new}}{BW}\ \le\ T_c$$

$r_{new}$ 是**这一块必须新搬的字节**（不是全部字节——已驻留的可复用），$T_c$ 是两块之间你能拿来等的时间。**这个式子是可算的，不是可调的。**

**两条同时成立 ⇒ 流式可行；只成立一条 ⇒ 必然有一类负载会崩。**

### 推论：一条"断崖"和一条"斜坡"

同一个系统在带宽下降时的表现**形状不同**：

- **按需（on-demand）**：停顿时长 $\approx r_{new}/BW$，随带宽**线性变差**——是斜坡，任何带宽下都停，但停得可预测；
- **预取（prefetch）**：在 $BW > r_{new}/T_c$ 时**停 0**，低于这个点**断崖式变差，而且可能比按需更差**——因为**跑输了的预取会占住读通道**，遇到突发需求时最坏的那一帧等得比按需还久。

> 实测样本（WorldPager，b1_ws 轨迹）：0.1 GB/s 下预取的 P50 是 75.9 ms、**P99 是 2621 ms**；同条件下按需换入的 P50 是 1130 ms、**P99 是 2424 ms**。**P50 赢 15 倍，P99 输 8%。**

**这条结论很反直觉，但它对所有预取系统都成立**：预取把"平均"做漂亮了，代价是"最坏"可能更坏。**所以流式系统的验收指标必须是 P99（甚至 max），不能是中位数。**

### 漏块怎么办：阻塞还是将就

| 策略 | 行为 | 代价 | 适用 |
|---|---|---|---|
| **阻塞** | 等到块到齐 | 一次卡顿，时长不可控 | 正确性不能降级（碰撞、判定） |
| **将就（stale fallback）** | 用上一份旧数据 | 结果**晚一拍**，但永不停 | 感知可容忍（画面、记忆检索） |

**这是一条产品决策，不是技术决策。** 判据：**"晚一拍"能不能被看见？** 画面能，判定帧不能。

### 缓存不能和预算抢同一份内存

一个具体的坑：**用页缓存/系统缓存"加速"IO，等于把磁盘 I/O 变成内存占用**。在一个按内存卡死的预算里（cgroup / 主机内存池），这是自相矛盾——所以真正做流式的系统会显式绕过它（`O_DIRECT`、`FILE_FLAG_NO_BUFFERING`、UE 的 IoStore）。

**判据：如果你的预算是"总内存"，那么任何"缓存"都是在预算内花钱买速度，而这笔汇率通常没人算过。**

### 会话越长越慢，是同一类病

容量随会话线性增长（$N\cdot B_c$）是一个病；**每次操作的代价随 $N$ 增长**是另一个病，而且更隐蔽——它不会崩溃，只会慢慢变慢。典型症状：每次都要扫全表（找受害者、选检索集）。**解法一律是"把 $O(N)$ 变成 $O(\log N)$ 或 $O(1)$"**：惰性堆、向量化、增量维护。

**这条在游戏里对应"实体数涨了之后每帧遍历所有实体"**——同一个病。

## Historical Evolution

```text
1960s  虚拟内存 / 分页：**第一个流式系统**，判据第一次出现（工作集 vs 驻留集）
1990s  图形学的 out-of-core 渲染：几何 / 纹理装不进显存，靠 LOD + 分块预取
2004  Virtual Texture（id Tech / 之后的 sparse virtual texture）：**纹理不再整体驻留**
2012  UE4 的 Texture Streaming / Level Streaming：按可见性与距离分级
2019  UE5 World Partition + Nanite + Virtual Shadow Map：**"流式"从加载策略变成架构**
2023  vLLM 的 paged KV：把操作系统的分页搬到推理框架里
2024  StreamingLLM：**记忆 = 一个定长窗口 + attention sink**（"定长化"这条路）
2025  FlexGen / InfiniGen / CachedAttention：KV 在 GPU/CPU/盘之间搬
2026  ★ 这一族在生成式内容上闭环：
        · WorldKV / ReWorld：按位姿检索历史 KV，放主机内存
        · WorldPlay：不存，重算（用算力换容量）
        · WorldStream：语义前沿 vs 实现前沿，**几何可再生、记录才是资产**
        · UniWorld：把状态设计成**定长**（显存上界与时长解耦）
        · WorldPager：int4 KV + GPU/DRAM/NVMe 三层 + 位姿预取，**零停顿 37.5 分钟**
```

**这条线的方向**：从"**怎么装得下**"到"**装不下的那部分该用什么换**"。三个答案已经很清楚——**压缩（常数倍）/ 重算（算力）/ 分层（空间）**，而只有后两个是无上限的。

## Related Concepts

- [[Budget Units]] — 容量与流量是两种计价对象，**混着算就等于允许拿容量换流量**；
- [[Scalability and Quality Tiers]] — 流式的"档位"是**驻留半径**（近处高精度、远处低精度），这与分辨率档位是两个独立的轴；
- [[Overdraw]] — 流式解决"装不下"，overdraw 解决"画太多"，两者都在填同一张填充率预算；
- [[Procedural Content Generation]] — "重算"这条路的极端形态：**根本不存，每次生成**；
- [[Niagara]] — 预热（warmup）是"用计算填窗口"，与流式的"用搬运填窗口"是同一个模式的两种实现。

## Technologies

- **虚拟纹理 / Sparse Virtual Texture**：纹理页 + 页表 + 按需驻留；
- **UE World Partition / Level Streaming**：按格子与距离流送；
- **IoStore / `O_DIRECT`**：绕过页缓存的读路径；
- **paged KV / KV offload**（推理侧）：把操作系统的分页搬到张量上；
- **双缓冲 + 后台回写**：把驱逐搬出关键路径。

## Game Applications

| 场景 | 访问集可先验吗 | 窗口 $T_c$ | 漏块怎么办 |
|---|---|---|---|
| 开放世界地形/植被 | ✅ 玩家位姿 + 速度外推 | 一帧（16.7 ms） | 降级到低模（将就） |
| 纹理流送 | ✅ 可见性 + 距离 | 数帧 | 降 mip（将就） |
| 关卡切换 | ✅ 设计好的 trigger | 数秒（可遮罩） | 阻塞（可接受） |
| **技能 VFX 首次播放** | ✅ 技能时序在配置里 | **前摇（0.2–0.5 s）** | **不能将就**（缺失=bug） |
| 玩家输入驱动的世界模型 | ⚠️ 位姿可外推，动作不可 | 一个 chunk | 用旧记忆（将就） |

**最后一行标 ⚠️ 是有意的**：**"位姿可预测"与"动作可预测"是两件事**。WorldPager 只外推位姿，动作靠"反正漏了也能用旧集合"兜住——这个设计之所以成立，是因为**它把不可预测的那一半交给了 fallback，而不是交给了预测**。**这是所有流式系统都该学的一招：不要去预测不可预测的东西，给它准备一个便宜的退路。**

## Personal Knowledge

`Normal`。已经掌握的：容量的线性增长、分层的形状、预取的收益。

**还没打通的一处**：**"窗口 $T_c$ 到底有多长"在你的系统里是个未知数。** 对渲染是 16.7 ms，对世界模型是 1.25 s，对关卡加载是数秒——**而技能 VFX 的窗口是"前摇"**，这个数在技能配置里是有的，但从来没被当成"流式窗口"用过。

## Learning Gap

- **没算过自己项目的"零停顿带宽下界"**：$\text{需求带宽}=r_{new}/T_c$。这个数一算出来，就知道"要不要预取"以及"预取要多少带宽"；
- **没有 P99 视角的流式验收**：现在的验收多半是"平均帧时间"，而流式的失效方式是**尾部**；
- **"容量 / 流量"两张表还没分开**：见 [[Budget Units]]（"容量"这一种计价对象要拆成**驻留**与**流量**两半，绑的是两个不同的瓶颈）。

## Next Step

1. **拿一个 S 档技能，算它的"流式窗口"**：从技能开始到第一次出现特效的帧数（前摇）就是 $T_c$，特效资源总字节是 $r_{new}$，两者相除就是"要多少带宽才不卡"。**这是一个 5 分钟就能算完的数**；
2. **给现有的 overdraw / 粒子预算加一列"容量/流量"标注**：每一个上限到底约束的是"同时有多少"还是"每秒搬多少"；
3. **把"漏块策略"写进规格**：哪一类资源可以降级、哪一类必须阻塞。**这一条现在多半是隐式的（"反正不会缺"）。**
