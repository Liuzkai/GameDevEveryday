# Profiling and Measurement

> **你测的不是时间，是某个计数器在某个域里数出来的东西。**
> 这一页要解决的不是"怎么用 RenderDoc"，而是**"这个数能支持什么结论、不能支持什么结论"**。

## Definition

测量 = **把一个"感觉卡"变成一个可反驳的数**，并且同时说清三件事：

1. **数**是多少；
2. 它在**哪个域**里数出来的（玩家等的那一帧？某个 pass？某条指令？）；
3. 它的**分辨率**是多少（这个数能分辨多小的差）。

> **本页的核心断言：任何性能数字都是一个三元组 $(\text{值},\ \text{域},\ \text{分辨率})$。缺一个，这个数就不能用来做决定。**

## Core Principle

```
                     ┌── 谁在数（域）───────────────┐
一个性能结论的可信度 ←──┼── 数得准不准（分辨率）───────┼── 三项都成立，结论才成立
                     └── 差是不是真的（偏差/统计）──┘
```

三者是**乘法关系**，不是加法：**任何一项接近于零，结论就接近于零**。
- 域错 ⇒ 数再准也没用（"GPU 时间少了 2 ms"可能只是把这 2 ms 挪到了 CPU）；
- 分辨率不够 ⇒ 你看不见要看的效应（0.05 ms 的改动淹没在 0.3 ms 的抖动里）；
- 偏差太大 ⇒ 你看见的效应是别的东西（布局、频率、驱动版本）。

## 三个计数域（先认域，再读数）

| 域 | 数的是什么 | 典型来源 | 分辨率 | 主要偏差 | 能回答 | **不能**回答 |
|---|---|---|---|---|---|---|
| **① 帧间隔**（present → present） | **玩家实际等的那一帧** | 引擎 frame stats / PresentMon / `stat unit` | 1 帧（16.7 ms @60） | vsync、合成器、驱动队列、窗口失焦 | "玩家感觉多卡" | 钱花在哪个 pass |
| **② Pass 时间戳** | GPU 上**某个区间**的耗时 | RenderDoc / PIX / Nsight 的 GPU duration | 亚微秒（但**回读有 2–3 帧延迟**） | **区间串行化**（测了它就变慢）、跨 pass 重叠被记到某一个头上 | "哪个 pass 最贵" | "为什么贵"（除非配计数器） |
| **③ 微基准** | **硬件常数** | 自己写的、只干一件事的 kernel | 周期级 | 脱离了真实负载（无 cache 污染、无 TLB 压力） | "硬件的边界在哪" | "你的帧为什么慢" |

> **判据一：先问"这个数是哪个域数的"。**
> 同一个词 "GPUTime"，在三个工具里可以是三个不同的量：**引擎自报的**（含提交等待）、**抓帧工具的**（区间被串行化后的）、**微基准的**（裸硬件）。**名字一样不等于域一样。**

## 两种失效：分辨率 与 偏差

### 失效 A — 分辨率不足（你根本没看见）

三种来源，都在游戏里天天发生：

| 来源 | 表现 | 数量级 |
|---|---|---|
| **量化** | timer 的最小刻度 | 亚微秒（多数平台够用） |
| **回读延迟** | 改一个参数，读数要等 **2–3 帧**才反映 | 33–50 ms —— **足以让你把 A 的效果记到 B 头上** |
| **区间串行化** | 每个 pass 单独计时 ⇒ GPU 被迫在 pass 之间同步 | 可让总时间**变长**；per-draw 计时尤其严重 |

**推论**：**你不能用"逐 pass 计时"去验证"整体省了多少"**——前者会改变后者。

### 失效 B — 偏差（你看见的不是它）

三类偏差，从"可控"到"难控"：

| 偏差 | 例子 | 怎么处理 |
|---|---|---|
| **选择偏差** | 只报最好的一次；只跑最有利的场景；只统计"稳定后"的帧（把加载/编译排除掉） | 预先声明口径；报 $P_{50}/P_{95}$/最差，不只报最好 |
| **环境偏差** | 频率/温度/后台进程/驱动版本/电源模式 | 固定清单；记录在报告里 |
| **布局偏差** | 代码/栈/堆的精确排布 ⇒ 同一份逻辑、不同二进制，差几个百分点 | **要么控制（固定链接顺序），要么随机化（见 STABILIZER）** |

**布局偏差的量化，是本页最硬的一条外部证据**：[[Curtsinger 2013 — STABILIZER Statistically Sound Performance Evaluation|STABILIZER]] 在 SPEC CPU2006 上发现，把布局随机化之后，LLVM 的 `-O3` 相对 `-O2` 的提升**与随机噪声不可区分**。也就是说：**一个"优化等级"的全部收益，可能还不如布局的抖动。**

> **判据二：差异必须大于仪器噪声才有意义。先测噪声底，再谈提升。**
> 噪声底的测法：**同一份构建，跑 30 次**，看 $P_5$–$P_{95}$ 的跨度。跨度 6% 时，"快了 3%" 不是结论。

## 归因三法（"贵在哪"的三种问法）

| 手段 | 怎么做 | 得到什么 | 代价 / 陷阱 | 什么时候用 |
|---|---|---|---|---|
| **消融** | 关掉 / 换成 0 / 换成常量 | "这一项值多少"（**含它引发的连锁**） | 会改变画面与合法性；关掉阴影可能让别的 pass 变快 ⇒ **测到的是"没有它时的系统"，不是"它的成本"** | 粗定位，第一刀 |
| **缩放** | 分辨率 / 数量 / 迭代数 ×2 | **标度律**（线性 / 饱和 / 常数） | 要多跑几次；只在标度区间内有效 | **建预算模型**（"翻倍会怎样"）——这是 [[Budget Units]] 的原料 |
| **计数器** | occupancy / stall reason / 带宽利用率 / L2 命中率 | "哪类资源先见底" | 需要解释能力；计数器本身有口径（见下） | 精定位，第二刀 |

**三法的分工**：**消融告诉你"值不值"，缩放告诉你"会不会爆"，计数器告诉你"为什么"。** 顺序错了会浪费一整晚（先上计数器，往往得到一堆"你早知道"的数）。

> **判据三：每次测量的目的不是"得到一个数"，是"排除一条假设"。**
> 好的测量设计在跑之前就能说出："如果假设 A 成立，这个数会是 X；如果是 B，会是 Y。" **说不出 X 和 Y 的测量，跑完也读不出东西。**

## 游戏特有的四个陷阱

1. **异步重叠**：CPU 提交与 GPU 执行最多重叠 1–2 帧 ⇒ **"CPU 时间 + GPU 时间 ≠ 帧时间"**。判断谁在等谁，要看**谁先到**（GPU idle 还是 CPU 空转），不是看两个数相加。
2. **查询延迟**：改参数 → 等 2–3 帧 → 读数才变。**在两次改动之间不留够帧数，你会测到上一次的效果。**
3. **观测扰动**：per-draw / per-pass 计时会**拆散并行**。你测的是"被拆散后的渲染器"，不是"玩家跑的那个"。
4. **均值掩盖尾部**：60 fps 是均值；**卡顿是尾部**。16.7 ms 均值 + 每 3 秒一个 50 ms 尖峰 = "帧率达标、体验很差"（见 [[Temporal Stability and Artistic Intent]]）。

## 与预算的对偶关系

本库花了两个月建立"预算"这一侧（[[Budget Units]] 的十二种计价对象、[[Real-Time VFX Performance Budgeting]] 的五维表）。**测量是它的另一半，而且两者不是同一件事**：

| | 预算 | 测量 |
|---|---|---|
| 给什么 | **上限 + 分解** | **实测 + 归因** |
| 什么时候 | 事前（设计期） | 事后（运行期） |
| 失败形态 | 超支（超了但不知道超在哪） | 归因错误（知道超了但怪错了人） |
| 误差来源 | **模型误差**（没算进去的东西） | **仪器误差 + 统计误差** |

**预算与实测之差，必须拆成三项**，否则这个差没有信息量：

$$\underbrace{\Delta}_{\text{预算}-\text{实测}}=\underbrace{\delta_{\text{模型}}}_{\text{预算没算的}}+\underbrace{\delta_{\text{仪器}}}_{\text{计数器数错的}}+\underbrace{\delta_{\text{统计}}}_{\text{这次碰上好布局}}$$

> **三者的和一旦大于你要检测的效应，这次测量就是无效的**——不是"结果不理想"，是"**没有结果**"。

## Historical Evolution

```text
1960s–1990s  CPU 侧：硬件性能计数器 + rdtsc（读时间戳寄存器）成为标准工具
      ↓
2003–2007  GPU 侧第一次可编程计时：timer query（GL_NV_timer_query / D3D event query）
           ——从此"这个 pass 多贵"第一次可测，但**回读天生延迟**
      ↓
2007–2010  厂商 profiler 出现（CUDA Visual Profiler / PIX / GPUPerfAPI）；
           同期**微基准**路线开始：Wong et al.（ISPASS 2010）用 pointer chase 解剖 cache 几何
      ↓
2009–2013  **方法学转向**：Mytkowicz 2009 证明"布局偏差能让结论反转"；
           STABILIZER 2013 把随机化搬进运行时（本库已入库）
      ↓
2018       微基准成熟形态：Jia et al. 量出 Volta 全表（本库已入库）
      ↓
2020s      两件事同时发生：① 计数器普及（Nsight Compute 的 Speed-of-Light / stall reasons、
           Radeon GPU Profiler、PIX 的 timing capture）；② **引擎自建计时**（per-pass
           timestamp 环、GPU-driven 的间接计时）
           ——**但统计侧几乎没进游戏工业**：多数团队仍用"跑三次取平均"
```

**一条主线**：**工具越来越强，方法却几乎没变。** 2009 年那篇论文批评的"跑一次就下结论"，在今天的游戏性能评审里仍然是默认做法。

## Important Papers

| 论文 | 它给了什么 |
|---|---|
| [[Jia 2018 — Dissecting the NVIDIA Volta GPU Architecture via Microbenchmarking\|Jia 2018]] | **仪器侧**：测延迟要消灭并行、测带宽要制造并行；stall-until-wrong 的"用正确性当尺子"；Volta 的 28 / 193 / 375 / 1029 四级台阶 |
| [[Curtsinger 2013 — STABILIZER Statistically Sound Performance Evaluation\|Curtsinger 2013]] | **偏差侧**：一个二进制 = 布局空间的一个样本；运行时重随机化让分布变高斯；`-O3` vs `-O2` 与噪声不可区分 |
| Mytkowicz et al. 2009《Producing Wrong Data Without Doing Anything Obviously Wrong!》（ASPLOS'09，**本库未入库**） | 偏差的**命名与调查**：环境变量长度 / 链接顺序就能反转结论；调查 133 篇论文无一处理 |
| Wong et al. 2010《Demystifying GPU Microarchitecture through Microbenchmarking》（ISPASS'10，**本库未入库**） | 微基准解剖 GPU 的**方法源头**（本库只经 Jia 2018 转引，未核全文） |
| Mei & Chu 的 fine-grained p-chase（经 Jia 2018 引用 [12]，**本库未入库**） | **把地址当自变量**的扫描方法；图 3.2 的台阶就是它画出来的 |

## Technologies

- **抓帧**：RenderDoc（跨平台）、PIX（Xbox/Windows）、Xcode GPU Capture（Metal）；
- **计数器**：Nsight Compute / Nsight Graphics、Radeon GPU Profiler、Arm Streamline；
- **帧呈现侧**：PresentMon、引擎自带 frame stats、`stat unit`；
- **微基准**：CUDA/HLSL compute kernel + 时钟寄存器读取（`clock64()` / `CS2R`）。

## Game Applications

- **画质档位的验收**：每档的差必须大于噪声底，否则"这档省了 2%"是幻觉；
- **性能回归 CI**：同一构建跑 N 次 + 报区间，比"跑一次比均值"可靠一个量级；
- **特效预算的实测侧**：五维表的每一项都要有"域 + 分辨率"标注（例：`OverDraw` 是**像素覆盖**，不是时间）；
- **平台对比**：PC 与移动端的"周期"含义不同（wave 大小、tile 内存），**不要跨架构引用周期数**。

## Personal Knowledge

**Normal。** 你在**工具层**是 Easy（RenderDoc / 平台 profiler / 五维表都熟），**缺的是三层**：

1. **域的分辨**：你现在的五个指标（Particles / DrawCalls / Primitives / OverDraw / CPUTime / GPUTime）里，**只有后两个是时间**，前四个是**计数**——它们与帧时间的关系要靠"单价"换算，而单价随架构变；
2. **噪声底**：还没有一次"同一构建跑 30 次看分布"的记录；
3. **统计侧**：没有把"提升 3%"与"布局抖动"分开过。

## Learning Gap

- **缺一次噪声底实测**：同一份构建、同一场景、跑 30 次，给出 $P_{50}/P_{95}$ 与极差；
- **缺一次"消融 vs 缩放"的对照**：同一个特效，分别用"关掉"和"数量减半"测，看两个数差多少（差多少 = 连锁效应的价格）；
- **缺 GPU 侧的测量偏差研究**：本库有 CPU 侧的 STABILIZER，**没有任何一篇做"GPU 布局/驱动版本偏差"**——这是一个真实空缺；
- **缺"per-pass 计时会不会改变总时间"的实验**：把同一个场景在"开/关 per-pass 计时"下各跑 30 次，量出观测扰动的价格。

## Next Step

1. **30 分钟**：挑一个 S 档技能场景，**同一构建跑 30 次**，记录帧时间，算出 $P_{50}$、$P_{95}$、极差。**这一步没有技术难度，但它会永久改变你看性能数字的方式。**
2. **15 分钟**：把五维表（[[Real-Time VFX Performance Budgeting]]）的每一行标注"域"——是计数还是时间？如果是计数，单价从哪来？
3. **按需**：给团队的性能评审模板加两行——"噪声底"与"样本量"。

- **建页依据**：`grep -ril "profiling\|profiler"` 命中 12 个文件，**0 个概念页承载**；而"预算"侧已有 12 种计价对象、8 组可引用数字——**两侧严重不对称**。
- **一个尚未回答的问题**：**为什么统计侧进不了游戏工业？** 一个可能的原因：游戏的性能目标是"最差帧"（极值），而统计工具擅长"均值"（中心）。**极值的置信区间要难得多**——这可能是 [[Temporal Stability and Artistic Intent]] 与 [[Curtsinger 2013 — STABILIZER Statistically Sound Performance Evaluation|Curtsinger 2013]] 之间真正缺的那篇论文。
- **2026-11-23 的首个推论**：**测量不是"读一个数"，是"选一个域"**。同一次改动，在三个域里可以是"更快 / 差不多 / 更慢"——**这不矛盾，这是三个问题**。
