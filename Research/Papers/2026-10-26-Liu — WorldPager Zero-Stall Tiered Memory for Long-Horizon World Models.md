# WorldPager: Zero-Stall Tiered Memory for Long-Horizon World Models on a Single Consumer GPU

## TL;DR

**交互式世界模型"记不住"不是因为模型不够大，是因为显存装不下它自己的记忆。** 这类系统为了"回到走过的地方还认得"，会把每个历史 chunk 的 KV 留下来做检索记忆——于是这份记忆**随会话时长线性增长**，而它要解决的问题（一致性）本身与时长无关。

本文最硬的一句判断，是把这件事故意和 LLM 的 KV offload 对照起来：

| | LLM 解码 | 交互式世界模型 |
|---|---|---|
| 单步计算 | 短（一个 token） | **长（≈1.2 s / chunk）** |
| 真正的限制 | **搬运带宽** | **容量**（chunk 21 / 60 / 226） |
| 访问集 | 查询算完才知道（要投机） | **算之前就知道**（相机位姿是输入） |

这两条一旦成立，问题就从"怎么搬得更快"变成"**怎么在装不下的前提下一直不停**"。作者在一台 **RTX 4090 + 32 GiB 主机内存 + 一块 NVMe** 的消费级机器上，把 Matrix-Game 2.0 的连续生成从 **45 秒**（主机 bf16 上限）推到 **37.5 分钟（3000 个 chunk）**，**停顿为零、主机内存恒定**，代价是 9.5 fps。

三个数字记住就够：
- 一个 chunk 的 KV = **486.6 MB（bf16）/ 129.4 MB（int4）**；重算一个被检索的 chunk = **585.5 ms**，从 NVMe 读回来反量化 = **10.9 ms**（**53.7×**）；
- 预取把停顿的中位数压到 0 一直撑到 **0.25 GB/s** 带宽；按需换入在任何带宽下都停（1.0 / 0.25 / 0.1 / 0.05 GB/s → 116 / 454 / 1130 / 2256 ms）；
- **但在 0.1 GB/s 以下，预取的 P99 反而比按需换入更差**（2621 vs 2424 ms）——**跑输了的预取会占住读通道**。这是全文最诚实、也最可迁移的一条。

> 一句话对读者：**"容量"和"带宽"是两个不同的预算，绑的是两个不同的瓶颈。** 你的技能 VFX 预算表里"同屏粒子数上限"是容量约束，"填充率 / overdraw"是带宽约束——把它们的数字混在一张表里比较，等于拿升和公里每小时比大小。

**读图**：横轴是"会话能生成多少个 chunk"（对数），六根柱子是同一条轨迹上的六种存储方案。看两件事：① 前三根（GPU / 主机 bf16）的差距是 **21 → 60 → 131**，而它们只差"放在哪、用什么精度"——**容量墙是可以靠搬家推后的，但推不远**；② 虚线是**位置墙（341 chunk / 4.3 分钟）**，它与内存无关，任何不带位置处理的方案都撞在这条线上。最后一根 3000 是本文。（图 1，Liu & Xue 2026）

## Problem

交互式世界模型按 chunk 自回归生成：一个 chunk = 3 个 latent 帧 = 12 个视频帧 = 0.75 s（16 fps），4 步去噪。为了"回去还认得"，检索式记忆把历史 chunk 的 K/V 全部留着，新 chunk 按相机位姿挑 $k=3$ 个历史 chunk 去 attend。

于是 **记忆是线性增长的，而"一致性"这个目标是不增长的**。Matrix-Game 2.0 有 30 层，一个 chunk 的 KV 在 bf16 下 **486.6 MB**：

| 存放位置 | 精度 | 装到第几个 chunk | 视频时长 |
|---|---|---|---|
| GPU（24 GB） | bf16 | **21** | 16 s |
| 主机内存 32 GiB | bf16 | **60** | 45 s |
| 主机内存 32 GiB | int4 | **226** | 2.8 min |
| 主机内存 64 GiB | int4 | **496** | ~10 min（墙钟） |
| —— 位置墙 —— | 任意 | **341** | **4.3 min** |

还有第二堵墙：MG2 用 1024 个 latent 帧的旋转位置表，**到 341 个 chunk 生成直接失败**，与内存系统无关。

## Historical Context

```text
2023  3DGS 之后，"世界模型 = 逐 chunk 生成的视频"成为一条独立路线
2024  StreamingLLM：把 attention sink 的 KV 钉住、窗口滑动——"记忆 = 一个定长窗口"
2024  WorldKV：按相机位姿检索被逐出的 KV，**存在 GPU 或 CPU 内存**；作者自陈"主机→设备传输延迟限制了 CPU 卸载变体"
2025  ReWorld：训练时就带一个**有界 landmark bank**，在 pinned 内存里预取"离当前位姿最近"的
2025  OmniMem：按 head 检索历史，GPU 上放小 LRU，缺块**要等**
2025  WorldPlay：**不存 KV，存帧，每个 chunk 重算一次**（8×H800 上实时）
2026  Rolling Forcing / Deep Forcing：把检索到的上下文**重新指派位置**，压到当前帧附近
2026  ★ 本文：把 KV 放进 **GPU / pinned DRAM / NVMe 三层**，按**外推位姿**预取，miss 不等待
```

**它的历史位置**：这一族论文此前都在回答"**新 chunk 该看哪些历史**"（检索策略），本文第一次把问题下沉一层，回答"**这些历史放在哪、什么时候搬**"。这个下沉很关键——因为上层策略（WorldKV / ReWorld / OmniMem / WorldPlay）全都可以接在它上面。

## Previous Work

| 路线 | 代表 | 存什么 | 放在哪 | 缺块时 | 会话能多长 |
|---|---|---|---|---|---|
| GPU 常驻 | WorldKV 风格 | KV（bf16） | 显存 | — | 21 chunk |
| 主机常驻 + 预取 | ReWorld 风格 | KV（bf16） | pinned DRAM | 等/降级 | 60 chunk |
| 按 head 检索 | OmniMem | KV 子集 | GPU LRU + DRAM | **等** | 受 DRAM 限 |
| 存帧重算 | WorldPlay | **latent 帧** | — | 重算 | 位置墙 341 |
| 量化 | QuantWM / Quant VideoGen | 2–5 bit KV | DRAM | — | 常数倍推后 |
| LLM 卸载 | FlexGen / InfiniGen / CachedAttention | KV | GPU/CPU/盘 | 投机/等 | — |
| **本文** | — | **int4 KV** | **GPU + DRAM + NVMe** | **不等，用上一 chunk 的集合** | **3000 chunk** |

**关键分野在"访问集什么时候可知"**。LLM 解码里，下一步要哪些 KV 取决于还没算出来的 query，所以 InfiniGen 只能**排练下一层的 attention** 去投机；世界模型里检索键是**相机位姿**，而位姿是**玩家输入的函数**——它在算之前就存在。

原文那句值得抄下来：

> "An operating system cannot prefetch reliably because the future page-reference string is unknown; here the control input makes that reference string known one chunk ahead."

**这就是"流式"能不能成立的第一个条件**（见 [[Streaming]]）。

## Core Idea

**先把这件事测量成一个"容量问题"，再用五条一阶公式把它变成一张设计表。**

| 常规做法 | 本文做法 | 换来什么 |
|---|---|---|
| 缺块就重算（WorldPlay） | **存 int4 KV**，缺块就反量化 | 585.5 ms → **10.9 ms**（53.7×） |
| 一层存储，装不下就停 | **GPU / pinned DRAM / NVMe 三层** | 226 → **3000** chunk |
| 缺块才去读（按需换入） | **按外推位姿提前一个 chunk 预取** | 停顿 60.2 ms → **0** |
| miss 就等 | **miss 用上一 chunk 的集合（stale-set fallback）** | 保证"永不等待"，代价是"可能晚一个 chunk" |
| 同步驱逐 | **后台回写 + 双缓冲** | +102.0 ms → **+1.8 ms** |

## Technical Approach

### 1) 五条一阶公式（全文的骨架）

设 $B_c$ 为每 chunk 字节、$T_c$ 为 chunk 计算时间（也就是**可以藏一次搬运的窗口**）、$P$ 为主机池大小、$r_{new}$ 为本 chunk 必须从 NVMe 新读的字节：

$$N_{fit}=1+\left\lfloor P/B_c\right\rfloor \tag{1}$$
$$\text{stall}_{prefetch}\approx\max\!\left(0,\ r_{new}/BW_R-T_c\right) \tag{2}$$
$$\text{stall}_{on\text{-}demand}\approx r_{new}/BW_R+o \tag{3}$$
$$BW_W\ge B_c/T_c \tag{4}$$
$$\text{NVMe use}\ge (N-N_{fit})\cdot B_c \tag{5}$$

MG2 + int4 代入：$B_c=129.4$ MB、$T_c\approx1.25$ s、稳态 $r_{new}\approx121.5$ MB ⇒ **预取在 0.1 GB/s 附近失效**，回写只需 **0.11 GB/s**。也就是说：**一块普通 SATA SSD 的带宽都够，缺的是容量**。

这套模型的价值不在"准"，在于**它在跑之前就能告诉你哪个设计会先撞墙**。Table III 里每个组件都对着一条公式：存 int4 对 $B_c$、三层对式 (1)、预取对式 (2) 的零停顿条件、后台回写对式 (4)、位置处理对那堵 341 的墙。

**验证方式是"预注册"**：作者先用模型对**没参与建模的配置**写死预测，再跑。结果 **8/8** 个溢出点预测落在 ±1 chunk 内、**15/15** 个"会不会停"判对、9 个非零停顿里 **7 个**在 30% 以内、MG2 上 **22/24** 条注册判据达成。**并且把三次失手也写出来了**：

- b1_ws 在 0.1 GB/s（恰在预测的失效带宽 0.103 GB/s 上），实测 75.7 ms vs 预测 38.1 ms——**在相变点附近式 (2) 的两项几乎相消，小误差被放大**（限速器少给 3.7% ≈ 多 50 ms）；
- LingBot 在 0.075 GB/s 高估 71%（448.5 vs 262.6 ms）；
- 240-chunk 回程 NVMe 读取量低于预测 26.6%（2.20 vs 3.0 GiB）。

### 2) 三层存储的工程细节

| 层 | 放什么 | 关键决定 |
|---|---|---|
| GPU（24 GB） | attention 窗口 + **staging slots** | staging 槽是"预取的落点"，不是缓存 |
| pinned DRAM 池 | int4 block | 池大小 = 预算 − 进程基线 − 2 GiB 余量 = **27.2 GiB** |
| NVMe | int4 block | **`O_DIRECT`**——否则 NVMe 流量会占 page cache，而 page cache **算在同一份预算里** |

存储与搬运的单位是"**一层一 chunk 一个 block**"（int4 下约 4.3 MB，4 KiB 对齐）。**写入一次；读回来仍是干净的，所以再次驱逐不产生写。**

这一条 `O_DIRECT` 是容易被忽略但决定成败的：**如果你用页缓存加速，你就把磁盘 I/O 变成了内存占用**——在一个 cgroup 卡死内存的场景里，这是自相矛盾。

### 3) 预取 + stale-set fallback

```
chunk c 在去噪（≈1.25 s）的同时：
    预取线程：外推位姿 → 跑检索策略 → 把选中的 block 从 DRAM/NVMe 搬到 GPU staging
chunk c+1 开始：
    如果策略在真实位姿下选的 block 都在 staging 里 → 直接 attend
    否则 → 不等待，复用 chunk c 的那套（stale set）
```

外推是**匀速**的。合成轨迹上（4 类运动、每类 50 条 × 800 chunk、90° FOV）命中率 **0.66–0.94**，而"复用当前位姿"只有 **0.03–0.52**。端到端两次跑的实际漏块率是 **0.010（yaw）/ 0.020（b1_ws）**——**漏 1–2%，靠 fallback 吃掉，不值得为它加等待**。

**这个设计的本质是一次交易**：用"**可能晚一个 chunk 的记忆**"换"**永不等待存储**"。在交互系统里这是正确的方向——记忆晚一帧没人看得见，卡一帧所有人都看得见。

### 4) 写回：把驱逐搬出关键路径

池满之后每个新 chunk 都要驱逐一个旧的。同步写会让每一帧都背一次 NVMe 写：

| 区间（256 chunk，32 GiB） | 同步驱逐 | 后台回写 |
|---|---|---|
| 3–225（池未满） | 0.0 ms | 0.0 ms |
| 225–240（开始驱逐） | **+102.0 ms** | **+1.8 ms** |
| 240–256（回程重访） | **+135.8 ms** | **+4.9 ms** |

两个实现细节也值得记：检索集选择**向量化**后在第 2900 个 chunk 是 **2.12 ms**（原 38.4 ms）；受害者选择用**惰性更新的堆**替代全表扫描，2000-chunk 回程的写回中位数从 **105.4 ms 降到 27.6 ms**，视频逐位相同。**这两处都是在修"每次操作的代价随会话长度增长"——和上面那个"容量随会话增长"是同一类病。**

### 5) 位置墙：扩展表 + 只对 key 重新旋转

不用重训，两步：

1. **扩展位置表**（8192 行，3000-chunk 会话用 12288）——在原生视野内**输出逐位不变**；
2. 跨过 341 之后，把检索到的 key **重新旋转**到"当前窗口之前"：最近的检索 chunk 放在当前 chunk 前 **30 帧**，更老的和 attention sink 连续排在它前面，**只旋转每个 head 的 44 个时间通道**，value 与窗口不动。规则是混合的——341 之前禁用，341 之后启用。

代价 +27 ms/chunk（3000-chunk 会话里表现为 341 处的一级 **+21.3 ms 台阶**）。**30 帧是扫出来的**：放太近（6 帧）或太远（96 帧）都更差。

## Key Contribution

1. **把"世界模型的记忆"重新定义成一个容量问题，而不是带宽问题**，并给出五条可预注册的一阶公式；
2. **第一次把世界模型的 KV 放到 NVMe 层**并做到零停顿预取；
3. **端到端的 37.5 分钟**：3000 chunk、停顿最长 **0.12 ms**、主机内存峰值 **30.7 GiB 且不增长**、写出 **334 GiB**；
4. **把"什么精度、给谁精度"做成了可分离的实验**（见下）。

### 今天最反直觉的一个结果：**均匀降精度 > 选择性保精度**

作者原本想按 head 挑：不同 head 对远距离上下文的依赖不同，那把"重要的 head"保 bf16 不就行了？测下来是反的：

| 方案 | 字节占比 | 记忆收益保留率 |
|---|---|---|
| **全部 head 用 int4** | **26.6%** | **105%** [102%, 108%] |
| 25% 的 head 保 bf16 | ~26% | **56%** [51%, 61%] |
| 用在线排序挑 head | ~26% | 58% |
| 随机一半 head 用 int4 | 13.3% | 70% |

**同样字节，差 48.1 个百分点，12 个 unit 全部成立。** 原文的结论句可以直接当判据：

> "Fidelity is better spent on every head at lower precision than on a few heads at full precision."

这条和你惯用的"把预算堆到最关键的 20%"直觉**方向相反**。它成立的前提是：**记忆的价值不集中在少数 head 上，而集中在少数 chunk 上**——作者也验证了这一点：只在"预测到要重访"时才恢复 head，同样的随机 25% head 从 56% 涨到 **81%**。

**所以真正的分布轴是"时间/事件"，不是"通道"。** 预算该按"什么时候用得上"分，不该按"哪个部件更重要"分。

## Why It Works

三件事同时成立：

1. **计算窗口足够长**（1.25 s），长到可以藏下一次搬运（1.46 GB 的搬运只需 276 ms）。LLM 解码没有这个窗口，所以它的 KV 卸载必须是"带宽优先"。
2. **访问集可提前一个 chunk 知道**，因为检索键是位姿、位姿是输入。这条把"投机"换成了"外推"，而外推的误差可以被 fallback 吸收。
3. **重算太贵、反量化太便宜**（585.5 vs 10.9 ms）。这条决定了"存"永远优于"算"——而 LLM 侧反过来（重算一个 token 很便宜），所以两边的设计不能互抄。

## Limitations

- **它不是实时**：37.5 分钟视频花了 63.2 分钟生成（9.5 fps，低于 16 fps 播放率）。作者自己写了 "WorldPager does not make MG2 real-time"。
- **单机、单种子、单起点**：所有计时来自一个起始图和一个种子，**不给置信区间**；轨迹只有两条合成轨迹（36 chunk）。
- **位置处理是"借来的"**：重新指派位置来自 StreamingLLM / Rolling Forcing / WorldPlay，作者明说 "We do not claim the idea"；而且**收益依场景而变**（scene 0003 上无测出效果）。
- **int4 的代价在长间隔重访上真实存在**：MUSIQ **−1.28**（长间隔，95% CI [−2.25, −0.36]），短间隔无差。**"无质量损失"只对短程成立**。
- **一个被点名的指标陷阱**：int3/int2 的 revisit LPIPS **更好**（128% / 120% 保留率），但 MUSIQ 掉 0.90 / 4.05——**更粗的 KV 让重访帧更像"第一次那一帧"，同时纹理变差**。这叫 copy effect。**LPIPS 单独读会得出反的结论**。
- **长程纹理漂移不是量化造成的**：约 100 chunk 后出现的斜向重复纹理，在 bf16 对照里同样出现（纹理能量比 0.97、MUSIQ −0.11）。**归因给"记忆条件生成"本身**。
- **第二个模型上检索没帮上忙**：LingBot-World 未用检索记忆训练，重访一致性没改善，故只报系统指标。**这限制了"通用性"的主张**。

## Game Development Relevance

**这篇是"流式"在生成式内容上的第一个严格样本，而流式是开放世界的母题。** 三处直接可用：

1. **容量 vs 带宽要分开记账**。你的项目里"同屏粒子 ≤ N"是容量，"overdraw ≤ k"是带宽，"贴图 ≤ 2048"是容量，"每帧上传字节"是带宽。**把它们混在一张预算表里，等于允许拿容量换带宽**——而这两者的失效方式完全不同（容量超了是崩溃/降级，带宽超了是掉帧）。
2. **"访问集是否可预测"决定你能不能预取**。玩家位姿可预测 ⇒ 世界模型/地形/植被可以预取；技能特效的触发时机由**技能设计**决定 ⇒ 也基本可预测（前摇、判定帧是配置里的数）；而"玩家下一步按什么键"不可预测。**这直接对应 UE 里 World Partition 的"按方向预载"和 Niagara 的"预热"两件事——它们是同一个判据的两个应用。**
3. **miss 的处理方式决定体验形态**。本文选"用旧的、不等"，代价是"记忆晚一个 chunk"。**这是所有流式系统的通用选择：你可以晚，但不能卡。** 反过来，如果你的系统里"晚一帧"是不可接受的（比如判定帧的碰撞体），那你就不能流式，只能常驻。

## Unreal Engine Relevance

- **World Partition / Level Streaming**：本文的三层（显存 / 内存 / 盘）与 UE 的（显存 / 内存 / pak）结构一致；`O_DIRECT` 那条对应"**别让 IO 缓存和你的预算抢同一份内存**"。UE 的 `-useioStore` / `FIoDispatcher` 走的就是绕过页缓存这条路。
- **Niagara 预热（Warmup）**：Niagara 的 warmup 本质是"在看不到的时候把状态算出来"，与本文"在上一个 chunk 计算的同时把记忆搬过来"是同一个模式；区别是 Niagara 用**计算**填预热，本文用**搬运**填。
- **不适用**：本文的"位置重映射"是 DiT 的旋转位置表特有的，UE 侧没有对应物。

## Technology Evolution

```text
"记忆放在哪"
2023  逐 chunk 生成 + 滑动窗口：记忆 = 一个定长窗口（StreamingLLM 式）
2024  WorldKV：按位姿检索被逐出的 KV，放 GPU 或 CPU —— **容量墙从 21 推到 60**
2025  ReWorld：有界 landmark bank + 主机预取 —— 仍然是"主机内存装得下"的前提
2025  WorldPlay：不存 KV，存帧、重算 —— **用算力换容量**（3.07× 一步去噪）
2026  ★ 本文：int4 + GPU/DRAM/NVMe 三层 + 位姿预取 + 不等待 —— **容量墙推到 3000**
        ↑ 换掉的不是精度，是"记忆必须常驻"这个前提
```

**这条线真正在动的东西**：从"**把记忆放小一点**"（量化、稀疏）到"**把记忆放到别处**"（分层、流式）。前者有常数上限（2 bit 就是 2 bit），后者**没有上限**——你只要愿意付盘的空间。**这是一次从"优化"到"改结构"的跳跃。**

**读图**：四个方框就是三层存储加计算。看三条边上的动作：① 从 pinned DRAM 到 GPU 的 `stage (prefetch thread)` 是**主动的**，由"位姿外推"驱动；② 从 NVMe 到 DRAM 的 `read` 只在池里没有时才发生；③ 右下角 `Background write-back thread` 从 DRAM 写回 NVMe，**完全在关键路径之外**。右边三行小字是设计的全部哲学：**miss 就用旧的、绝不阻塞；访问集提前一个 chunk 知道；写回不占关键路径**。（图 2，Liu & Xue 2026）
