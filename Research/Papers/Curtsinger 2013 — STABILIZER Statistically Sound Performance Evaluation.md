# Curtsinger 2013 — 一个二进制只是布局空间里的一个样本

## TL;DR

**"改之前 100 ms、改之后 97 ms"这句话不成立——因为一个二进制只是"所有可能布局"里的一个样本，你跑一万次也还是那一个样本。**

原因是硬的：cache 与分支预测器让性能依赖**代码 / 栈 / 堆的精确排布**。换一个链接顺序、多一个环境变量、堆上多分配 8 字节，都可能让同一个程序快慢差几个百分点——**而这个差值与"你的优化"在观测上不可区分**。

STABILIZER 的做法：**让程序在运行中每 500 ms 把自己的代码、栈、堆重新随机排布一次**。于是一次运行 = 布局空间里的许多个 i.i.d. 样本；由中心极限定理，总执行时间趋近**高斯分布**，参数检验（ANOVA）才有了前提。

结果（LLVM 3.1 + SPEC CPU2006，18 个 C/Fortran 基准，各跑 30 次）：

| 对比 | 逐基准显著 | 整套基准 |
|---|---|---|
| `-O2` vs `-O1` | **17 / 18** | 显著（但只在 **90%** 水平） |
| `-O3` vs `-O2` | 9 / 18 | **与随机噪声不可区分** |

> **一句话判据（今天最该记）：在说"我优化了 X%"之前，先测噪声底。**
> 如果同一份代码在不同布局下的散布是 5%，那么"3% 的提升"不是结论，是**抽样**。

## Problem

性能评估的标准做法是"改前跑一次、改后跑一次，比时间"。这在现代架构上**不成立**，原因不是"噪声大"，而是**样本量根本是 1**：

- cache 与分支预测器让性能依赖机器特定参数**和精确的布局**（代码段、栈帧、堆对象的位置）；
- 编译器优化**本身就会改变布局**——所以"优化带来的收益"与"优化顺带改了布局带来的收益"被混在一起，**无法分离**；
- 跑更多次没有用：**同一次编译产出的那个二进制，无论跑多少次，都只是布局空间里的同一个点**。

论文的原话是全篇最锋利的一句：

> *"A single binary constitutes just one sample from the space of program layouts, regardless of the number of runs."*

## Historical Context

这条线是**"实验方法学"**，不是"性能优化"：

```text
2003  Alameldeen & Wood：模拟器的多线程负载本身有方差（HPCA'03）
      ↓
2007  Georges et al.：Java 性能评估要"统计严谨"（OOPLS'07）——提出用多样本 + 置信区间
      ↓
2009  Mytkowicz et al.《Producing Wrong Data Without Doing Anything Obviously Wrong!》
      ——环境变量长度 / 链接顺序就能让 O2 vs O3 的结论反转；调查 133 篇论文，无一篇处理了偏差
      ↓
2013  本文：把"随机化"从"实验设计建议"变成"运行时机制"——不用改实验，改程序
      ↓
2010s+ 性能 CI 开始普遍要求"重复 + 显著性"；但**游戏侧几乎没有**（见 Game Development Relevance）
```

**它继承的是 Mytkowicz 的"setup randomization"**：既然布局是混杂变量，那就**把它随机化**，让它从"系统误差"变成"可以被平均掉的随机误差"。

## Previous Work（三个邻居，各缺什么）

| 工作 | 做了什么 | 缺什么 |
|---|---|---|
| 常规 A/B 计时 | 改前跑、改后跑，比均值 | **样本量 1**；布局差与效应混在一起 |
| Georges 2007 / 统计严谨评估 | 要求多样本、置信区间、避免多次 t 检验 | 假设"同一二进制的多次运行是独立样本"——**而它们共享同一个布局** |
| Mytkowicz 2009 | 证明布局/环境偏差能让结论反转，建议随机化实验设置 | 只在**实验侧**给建议（换链接顺序、改环境变量大小）；**每个配置仍是一个样本** |
| ASLR / DieHard（安全侧随机化） | 随机化地址布局（粗粒度、一次性） | 目的不是测量；**一次性**随机化只给出"另一个样本"，不给分布 |

**本文的增量**：**运行中反复重随机化**，让"一次运行"内部就包含许多独立布局样本 ⇒ 分布近似高斯 ⇒ 参数检验可用。

## Core Idea — 把布局从"固定混杂变量"变成"随机变量"

统计上只有两条路能处理混杂变量：**控制它**（固定住）或**随机化它**（平均掉）。布局控制不住（编译器、链接器、分配器都在动它），所以只剩随机化。

三个设计决定，每个都在解决一个具体问题：

| 决定 | 解决什么 | 代价 |
|---|---|---|
| **重随机化（每 500 ms）** | 一次运行内的多个区间是 i.i.d. 样本 ⇒ 总量服从高斯（CLT） | 重定位开销 |
| **三种布局都随机（代码 / 栈 / 堆）** | 只随机一种，另外两种仍是混杂变量 | 实现复杂（函数要可重定位） |
| **函数粒度 + 陷阱按需重定位** | 不用停机重排全部代码；只在"下次被调用"时搬到新位置 | 首次调用有 trap 开销 |

## Technical Approach

### 1. 代码随机化：trap + 按需搬家（图 3）

1. 初始化时在**每个函数开头放一条 trap**（图 3a）；
2. 函数第一次被调用 ⇒ 陷入运行时 ⇒ 在随机位置分配一份副本，连同**重定位表**（图 3b）一起放好；
3. 每 500 ms 定时器触发**重随机化**：在所有函数头重新放 trap（图 3c）；
4. 下一次调用时，运行时**遍历栈**，把仍在栈上的函数（有返回地址的）留下，其余释放；未来的调用指向新副本（图 3d）。

**这套机制的关键不是"随机"**，是**"随机得便宜"**：搬家只发生在"下一次调用"，所以热循环里的函数几乎不会被反复搬——重随机化的开销被摊到调用边界上。

### 2. 栈随机化：每次调用塞一段随机填充

每个函数调用时加**最多一页**的随机 padding（图 4），使栈帧的**绝对地址**随机。栈布局影响的是"哪些局部变量落在同一 cache set"。

### 3. 堆随机化：随机化分配器

用一个随机化的堆（shuffle 参数 $N=256$，通过 DieHard 同款随机性测试），使对象在地址空间里散开。

### 4. 统计：为什么"重随机化"能开 ANOVA 的门

- 一次运行 = 许多个随机布局区间之和；
- 由 CLT，**总时间 ≈ 高斯**；
- 高斯 ⇒ 可以用 ANOVA / t 检验，而不是只能靠非参数方法（后者对"小效应"几乎没有功效）。

**这一步是全文的枢纽**：随机化不只是"多采几个样"，它**改变了分布的形状**，从而改变了"你能用哪种尺子"。

## Key Contribution

1. **一句可复述的诊断**："一个二进制 = 一个样本"——把所有"跑了很多次所以很可信"的说法一击击穿；
2. **把随机化搬进运行时**：不需要重编 N 次、不需要 N 台机器，一次运行就采样布局空间；
3. **一个让所有人不舒服的结果**：LLVM 的 `-O3` 相对 `-O2`，在 SPEC CPU2006 上**与噪声不可区分**；
4. **一个可复用的方法**：任何"环境/布局是混杂变量"的性能问题，都可以问"能不能把它随机化掉"。

## Why It Works

| 条件 | 怎么满足 | 不满足会怎样 |
|---|---|---|
| **布局确实是主要方差源** | 论文的前提；实测中布局效应常常"dwarf all other sources of variance" | 若方差主要来自频率/热/邻居，随机化布局没用 |
| **重随机化足够频繁** | 500 ms 一次，一次运行里几十个区间 | 区间太少 ⇒ 不接近高斯 ⇒ 检验失效 |
| **随机化覆盖全部三类布局** | 代码 + 栈 + 堆都可独立开关 | 只随机一类 ⇒ 另两类仍偏 |
| **开销不改变结论** | 中位 6.7%，最坏 < 40%；且开销**对两个版本同等施加** | 若开销与版本相关（例如随机化对某类代码特别贵），会引入新偏差 |

**第四条最微妙**：STABILIZER 的开销不是"越小越好"的问题，而是"**是否与处理无关**"的问题。一个 6.7% 的、对所有版本一视同仁的开销，不破坏比较；一个 1% 的、只惩罚其中一个版本的开销，会。

## Limitations（七处冷水）

1. **结论有明确的适用域**：LLVM **3.1**、SPEC **CPU2006**、x86-64 / PowerPC、**2013 年**。它说的是"**在那一套编译器与基准上**，-O3 相对 -O2 不显著"——**不是"O3 普遍无用"**。
2. **"不显著"是整套基准层面的**。逐基准看，-O3 有 **9/18** 显著（其中 3 个是**变慢**）；不显著的是"跨整套基准的平均效应"。**把它读成"每个程序上都没差"是过度概括。**
3. **仪器本身在扰动系统**：论文自己承认随机化增加了 working set、加大了 cache 压力（cactusADM 尤其明显，堆随机化把对象分散导致浪费）。**测量改变了被测量。**
4. **覆盖不全**：不支持 C++ 异常 ⇒ 5 个 C++ 基准被排除（omnetpp、xalancbmk、dealII、soplex、povray）；5 个 Fortran 基准构建失败。**"全 SPEC"其实是"能编过的 SPEC"。**
5. **高斯是经验结论，不是定理**：Shapiro-Wilk 检验里仍有 2/18 不服从（cactusADM、hmmer；后者被归因于"对对齐敏感的浮点运算"）。**CLT 给的是渐近，样本有限时仍会破。**
6. **只控制布局偏差**，不控制频率、温度、邻居负载、NUMA。**它是"偏差清单"里的一项，不是全部。**
7. **不能进发行版**：随机化是为了测量，不是为了跑得快。**它是一台实验室仪器，不是运行时特性。**

## Game Development Relevance

**这篇论文一个字都没提游戏**，但它描述的失效模式在游戏性能工作里**天天发生**：

| 论文里的现象 | 游戏里的对应 |
|---|---|
| 链接顺序改变 ⇒ 代码布局变 ⇒ 性能变 | 换一个 UE 版本 / 改一个模块的加载顺序 / 打开 LTCG ⇒ **SASS 排布变了** |
| 环境变量长度改变 ⇒ 栈对齐变 ⇒ 性能变 | 命令行参数、日志开关、平台 SDK 版本 ⇒ **常量缓冲的对齐变了** |
| 堆对象位置改变 ⇒ cache set 冲突变 | 资源加载顺序、pak 内排序 ⇒ **纹理/缓冲落在不同 set** |
| "跑 30 次取平均"仍是 1 个布局样本 | "我在两台机器上各跑 10 次，都是 3% 提升" ⇒ **仍是 2 个样本** |

**可落地的三件事**（不改引擎）：

1. **先测噪声底**：同一份构建，跑 30 次，看**分布**（不是均值）。若 P5–P95 的跨度是 6%，那么 3% 的结论不成立。
2. **做"布局抖动"**：在 CI 里对同一份代码做 3–5 个**等价但布局不同**的构建（改链接顺序、加随机 padding、改模块顺序），看结论是否稳定。**这是 STABILIZER 思想的穷人版**，成本是一晚上构建。
3. **报告要给分布，不给单点**：`P50 / P95 / 最差帧` 三个数一起报——这也是 [[Temporal Stability and Artistic Intent]] 里"卡顿是尾部事件"的同一个要求。

**必须说明的边界**：游戏帧时间是**重尾**的（编译、加载、GC、shader 编译、平台调度都会制造长尾），**CLT 的"趋近高斯"在 1% low 上不成立**。所以 STABILIZER 的方法适用于"**稳态吞吐**"，不适用于"**卡顿**"——卡顿要另用极值统计。

## Unreal Engine Relevance

- **`stat unit` / `stat gpu` 的单帧读数不是样本**：那是"一个布局下的一帧"。要下结论，得看**帧时间分布**。
- **自动化性能测试**（Gauntlet / 自建 CI）：现在多数只比"平均帧时间"，等价于论文批判的做法。**加一步"跑 N 次 + 报置信区间"就能把它变成可辩护的结论**，不需要随机化布局。
- **Shader 编译结果的抖动**：同一份 HLSL，驱动版本变化会改 SASS 排布 ⇒ 帧时间变。**把"驱动版本"当成一个必须固定的混杂变量**（和论文里的"链接顺序"同类）。
- **不要**试图在游戏里做运行时重随机化：那是测量工具，不是优化手段。

## Personal Knowledge State

**Normal。** 统计侧的基础（均值/方差/显著性）你是 Easy；**需要练的是"把工程直觉翻译成样本量"**：当有人说"这个改动快了 3%"，你要能立刻问出三件事——**噪声底多大、样本是什么、混杂变量有哪些**。

## Learning Value

1. **"样本量"是一个物理量，不是次数。** 同一个二进制跑一万次，样本量还是 1。**这条判据能挡掉大量无效的性能争论。**
2. **随机化是处理混杂变量的唯一通用手段**（控制不住的时候）。
3. **仪器的开销要与处理无关**——这是"测量可信"的一个独立条件，和"开销小"不是一回事。
4. **显著性有层级**：逐项显著 ≠ 整体显著。**报告"不显著"时要说清是在哪一层。**

**读图**：四格是一次重随机化的完整生命周期。**(a)** 每个函数头放 trap（黑条）；**(b)** 被调用的函数搬到随机位置，后面紧跟**重定位表**（记录它引用的所有全局与函数）；**(c)** 定时器到点，所有函数头重新放 trap；**(d)** 下次调用时，运行时走一遍栈——**还在栈上的（foo′）保留，已经返回的（baz′）释放**，未来的调用指向新副本（foo″）。**注意 (d) 里 foo′ 标着 "on stack"**：搬家必须尊重"还有返回地址指着它"这件事，否则程序会崩。出处：Curtsinger & Berger 2013, Fig. 3。
