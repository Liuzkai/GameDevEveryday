# Jia 2018 — 用微基准把 GPU 的常数一个个"撞"出来

## TL;DR

**厂商不公布微架构细节，那就写一个只干一件事的 kernel，让硬件自己把常数漏出来。**

三个直接可用的数（V100，PCIe 卡，1.38 GHz）：

| 层级 | 实测延迟 | 相对 L1 |
|---|---|---|
| L1 命中（32 B 行） | **28 周期** | 1× |
| L2 命中（6 MiB） | **~193 周期** | 6.9× |
| 显存（L2 miss + TLB 命中） | **375 周期** | 13.4× |
| 显存（L2 miss + TLB miss） | **1,029 周期** | **36.8×** |

> **一句话判据（今天最该记）：测延迟要"消灭并行"，测带宽要"制造并行"。**
> 同一个硬件、两个数、两种失败模式——所以"这个 shader 是延迟受限还是带宽受限"这个问题，**本质是在问"你的并行够不够多"**，而不是在问硬件。

## Problem

厂商白皮书只给"峰值 FLOPS""带宽 GB/s""SM 数"，**不给**：缓存几何（几路组相联、多少组、行多大）、各级延迟、寄存器 bank 结构、指令编码格式、原子操作在竞争下的退化曲线。

缺这些数的后果是可测量的：论文开篇给了一个 8×8 的矩阵乘内核，**只改寄存器分配（消除 bank 冲突），单 SM 从 132.05 涨到 152.43 GFlops/s（+15.4%）**——编译器把 15% 落在了桌上，而**你看不见它，因为你看不见 SASS 的 bank 归属**。

这不是"调优技巧"，是**测量问题**：没有微架构常数，你无法判断一段代码"应该"多快。

## Historical Context

这条线不是"提出新算法"的谱系，是**"反向工程硬件"**的谱系——它的产出物是**常数**，不是方法：

```text
2007–2010  CUDA 公开后第一批微基准：Wong et al. 2010《Demystifying GPU Microarchitecture
           through Microbenchmarking》用 pointer chase 量出 Fermi/GT200 的 cache 几何
      ↓
2010s      Mei & Chu 的 fine-grained p-chase：把"步长"当自变量，把 cache 行边界画出来
      ↓
2014–2017  Kepler → Maxwell → Pascal 逐代复测（本文引用的 [9][11][12] 一族）
      ↓
2018       本文：Volta V100，66 页，把延迟/带宽/编码/原子/Tensor Core 一次量完
      ↓
2019       同一团队《Dissecting the NVidia Turing T4 GPU via Microbenchmarking》
           （arXiv:1903.07486，65 页）——同一套方法，换一代架构
```

**这条线最反常的地方**：它每次只值一篇技术报告（没有新算法、没有 SOTA 数字），但**每代架构都得重做一次**——因为常数会变，而且会变出反直觉的方向（见下）。

## Previous Work（三个邻居，各缺什么）

| 工作 | 做了什么 | 缺什么 |
|---|---|---|
| 厂商白皮书 / 架构图 | 给峰值、给 SM 数、给"L1 与 shared 合并"这类结构性描述 | **不给延迟、不给组相联、不给竞争下的退化**；峰值是"上限"，不是"你能拿到的" |
| Wong 2010 / Mei & Chu（p-chase） | 建立了"用指针追逐量 cache 几何"的方法 | 停在 Fermi/Kepler 一代；指令级（编码、bank、stall）没有覆盖 |

**本文的增量**：把"常数"从"散落在各代论文里的碎片"变成**一张同口径、可横向对比的表**（Volta / Pascal / Maxwell / Kepler 五张卡并排）。

## Core Idea — 两个方向相反的实验

这是全篇最值得抄走的方法论，而它只有两句话：

| 你要测 | 实验要做什么 | 为什么 |
|---|---|---|
| **延迟** | **消灭并行**：让每次访问都依赖上一次的结果（$a_i = \text{load}(a_{i-1})$） | 只要存在独立访问，硬件就会用 MLP/ILP 把等待填掉，你测到的是"吞吐"不是"延迟" |
| **带宽** | **制造并行**：足够多的独立访问 + 足够大的工作集 | 带宽是"饱和值"，不饱和就只是"这次拿到了多少" |

> **由此得到本库第一条"测量判据"**：**你测到的延迟，永远是"你能隐藏多少等待"的函数。** 只有把并行拿掉，才拿到裸延迟；一旦拿掉并行，这个数就**不再代表真实负载里的表现**——真实负载里延迟是被 occupancy 掩盖的。
> 所以"L2 是 193 周期"这句话的正确用法不是"所以很慢"，而是"**所以我需要至少 193/指令间隔 个 warp 才能把它藏住**"。

## Technical Approach

### 1. p-chase：把"地址"变成自变量（图 3.2）

指针追逐：数组里存成环，每个元素指向下一个，**下一个地址由上一个 load 的结果决定**。于是：

- 改变**步长**（相邻两次访问的地址差）⇒ 命中同一行 / 跨行 / 跨 set / 跨 TLB；
- 纵轴是**实测周期**，横轴是**地址**，图 3.2 就是一张"存储器地图"：

```
1029 ─  ●                                      ← 第一次访问：L2 miss + TLB miss
 375 ─           ●        ●        ●          ← L2 miss，TLB 命中
 193 ─     ●        ●        ●        ●       ← L1 miss，L2 命中
 128 ─                                        （纵轴刻度，不是数据）
  64 ─                                        （纵轴刻度，不是数据）
  28 ─  ●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●●  ← L1 命中
       0    32    64    96   128   160   192   224   256   （相对地址 / B）
```

**这张图的读法**：**大多数点贴在 28 上（L1 命中），少数几个点跳上去**——跳变的位置告诉你"在哪一步跨出了这一级的覆盖范围"，跳变的高度告诉你"下一级值多少"。原文的图注把四个跳变逐个点名：1029 = L2 miss + **TLB miss**，375 = L2 miss（TLB 命中），193 = L1 miss / L2 命中，28 = L1 命中。

> **注意横轴只有 256 B、点却很稀**：这不是"每 32 B 一个台阶"的行扫描，而是**在若干起始地址上各跑一条完整的追逐链**。**所以它给的是"四级台阶"（L1 / L2 / DRAM / DRAM+TLB），不是"行边界"**。想知道行多大，要看得更细的扫描（本文用 32 B 行、4 组、128 B 更新粒度这几项交叉验证）。

### 2. 指令延迟：拿"算错"当尺子

这是全文最漂亮的一招。SASS 的指令字里有**控制位（stall count）**，规定这条指令的结果要等几个周期才能被下一条用。于是：

> 把 stall 值一格一格往下调，**直到依赖它的那条指令读到的结果是错的**。最后一个"还算对"的 stall 值，就是这个指令的延迟。

**为什么这不是循环论证**：它没有用"时间"去测"时间"。它用的是**正确性**——硬件的时序约束被编码在指令字里，而"算错"是一个离散、无噪声、可复现的判据。

| 指令类 | Pascal | Volta | 备注 |
|---|---|---|---|
| IADD / FFMA / FMUL / SEL / MOV | 6 | **4** | 白皮书也承认 FMA 依赖延迟降到 4 |
| IMAD | **~86** | **5** | Pascal 上 IMAD/IMUL 是**模拟**的（本文明确说 "emulated"） |
| 半精度 HADD2/HFMA2 | 6 | 6 | — |
| 双精度 DADD/DMUL/DFMA | 8 | 8 | — |
| POPC | 14 | **10** | — |
| MUFU / FLO / BREV | 14 | 14 | SFU 侧 |

**表里最刺眼的一行是 IMAD：86 → 5。** 这不是"优化了 17 倍"，是**从"用多条指令模拟"变成"一条硬件指令"**——同一个写法，两代硬件上是两件完全不同的事。**这就是"没有常数就只能靠猜"的具体代价。**

对可变延迟指令（如 atomic），方法换一种：取一条**已知延迟**的指令做搭档，人为造出依赖，用 `CS2R`（读时钟寄存器）把"一对"括起来，再减掉已知的那一半。

### 3. 带宽：理论值来自白皮书，实测值来自 benchmark（图 3.10 / 3.11）

| 图 | 结论 |
|---|---|
| 图 3.10（shared memory） | 实测**贴着**理论上限（$P\cdot B_s\cdot w_s\cdot f_g$）——片上带宽"理论=可得" |
| 图 3.11（global memory） | 四张卡的实测柱**全部矮于**白皮书柱——显存带宽"理论≠可得" |

**这一对图的含义比数字重要**：**离 SM 越近，"理论值"越可信；越远，理论值越像"上限的广告"。** 所以任何"带宽利用率 80%"的说法，先问分母是白皮书还是实测。

### 4. 一个副产品：竞争才是原子操作的真价签

表 4.2（shared memory 原子加，单位周期）：

| 同地址竞争线程数 | V100 | P100 | K80 |
|---|---|---|---|
| 1（无竞争） | **6** | 15 | 93 |
| 8 | 18 | 30 | 952 |
| 32 | **66** | 78 | **4,257** |

**11 倍（6→66）** 与 **45 倍（93→4,257）** 是两种完全不同的硬件设计：Kepler 没有硬件 shared atomic（模拟），Volta 有。**而"原子操作很贵"这句经验，在无竞争时是错的（6 周期 ≈ 两条 FFMA）。**

## Key Contribution

1. **一张可横向对比的常数表**（五张卡、七个层级、十几个字段）——本库 [[GPU Architecture]] 的相对倍数表从此有了绝对刻度；
2. **两个方向相反的实验范式**（消灭并行 / 制造并行）——比任何单个数字都耐用；
3. **"用正确性当尺子"**——当计时器的分辨率粗于被测对象时，去找一个离散的、二值的判据（对/错），而不是去借更细的钟；
4. **把"编译器留下的 15%"标价**：+15.4% 不是靠更好的算法，是靠看得见 bank 归属。

## Why It Works

微基准之所以能当"常数"用，靠三件事，缺一不可：

| 条件 | 本文怎么满足 | 不满足会怎样 |
|---|---|---|
| **只变一个变量** | 每次只改步长 / 只改 stall / 只改寄存器编号 | 测到的是多个效应的卷积，无法归因 |
| **因果隔离** | 依赖链强制串行；同一行内的访问必然同延迟 | 并行把等待填掉，测到的是吞吐 |
| **可复现** | 同一块卡、固定时钟（1,380 MHz）、给出完整 benchmark 描述 | 数字变成"某次跑出来的" |

**第四条隐含条件**：**你测的东西必须真的在硬件上发生。** 本文所有结论都靠反汇编（SASS）交叉验证——不看机器码的微基准，很容易测到"编译器帮你删掉的那个操作"。

## Limitations（六处冷水）

1. **周期不是时间。** 全文单位是 cycle；换算成 ns 要乘 $1/1.38\,\text{GHz}\approx0.72$ ns。**同一个"193 周期"，在 1.0 GHz 的移动 GPU 上是 193 ns，在 1.38 GHz 上是 140 ns**——跨设备引用必须先换算。
2. **一块板、一代架构、一家厂商。** V100 PCIe、GV100、2018 年。作者自己写：*"our optimizations are specific to the Volta architecture… Our discovery work needs to be repeated anew on each future architecture"*。**这张表不能当"GPU 通用常数表"用。**
3. **微基准不是真实 kernel。** 追逐链里没有别的 warp 抢 cache、没有真实工作集的 TLB 压力、occupancy 是人为固定的。**它给的是"硬件的边界"，不是"你的帧的时间"。**
4. **+15.4% 那条路在游戏里基本不可行。** 它要求手改 SASS（作者也承认"substantial human effort"，只在"tight computational kernels"上值得）。**能抄的是"知道 bank 冲突存在"，不是"去改二进制"。**
5. **"理论带宽"来自白皮书**——那是一个文档，不是一次测量。所以图 3.11 的两根柱子严格来说不是"理论 vs 实测"，是"**厂商声明 vs 我们的实测**"。
6. **它不回答"我的帧为什么慢"。** 它回答"这块硬件的边界在哪"。从边界到归因，还差一整套 profiling——见 [[Profiling and Measurement]]。

## Game Development Relevance

- **同一段 HLSL，在两代卡上可以是两件事**：IMAD 从 86 周期（模拟）变成 5 周期（硬件），意味着"整数运算多"的 shader 在 Pascal 上被结构性惩罚。**跨代对比性能时，指令组合的变化可能比算法变化更大。**
- **移动端（TBDR）不要直接套这张表**：架构不同（tile 内存、HSR），且移动 GPU 的"L1"往往就是 tile buffer 的邻居。**表要重做，方法可以照抄。**
- **寄存器压力有了价格**：2 bank × 64-bit（Volta）意味着**三个源寄存器全落在一个 bank 就串行化**。这就是"寄存器用得越紧，越可能撞上 bank 冲突"的硬件原因。
- **原子操作的经验要分档**：无竞争 6 周期（便宜），32 线程同地址 66 周期（11×）。**粒子系统里"每个粒子 atomicAdd 到同一个计数器"的写法，成本全在这一列上。**

## Unreal Engine Relevance

- **Shader 复杂度评审**：把"指令数"换成"指令组合"——ALU 密集型看 FFMA/MUFU 比例，整数密集型看 IMAD 是否落到慢路径（老架构）。
- **Niagara GPU 粒子**：粒子计数器/排序用的原子操作，属于"高竞争"那一档；能改成分块归约（每个 warp 一个局部计数器）就绕开了表 4.2 最右列。
- **Compute shader 的 LDS（shared memory）使用**：shared 带宽"理论=可得"（图 3.10），所以**在 shared 上做 tile 化比在显存上做预取更可靠**。
- **不要用这张表去诊断**：它是"边界表"，UE 里的归因仍要靠 [[Profiling and Measurement]] 的三层仪器。

## Personal Knowledge State

**Normal。** 你能读懂表，也能把"28 / 193 / 375"和"L1 / L2 / 显存"对上——这一层是 Easy（写 shader 的人都有量级直觉）。**需要练的是两处**：① 把周期换算成"需要多少 warp 才能藏住"（$193/4\approx48$ 个 warp 才能完全掩盖 L2 延迟——这个数比"193"有用得多）；② 分清"边界"与"归因"，不要把这张表当成诊断工具。

## Learning Value

1. **测量方法的两个方向**：消灭并行测延迟、制造并行测带宽。**这条比表里任何一个数都耐用**，而且能直接搬到 CPU、搬到网络、搬到任何"有并行的系统"。
2. **当尺子比被测物粗时，去找一个离散判据**。"stall 调到算错为止"是这类技巧的原型：**用正确性代替时间**。
3. **"理论值"要问出处**。图 3.11 的两根柱子提醒：很多"效率"讨论的分母，其实是一份市场文档。

**读图**：橙柱是本文 benchmark 的实测，蓝柱是白皮书的理论上限。**四张卡的实测全部低于理论**——注意这不是"实现得不好"，而是"理论值本来就不是可达值"（刷新、行激活、bank 冲突都在里面）。对照图 3.10（shared memory）可以看到实测**贴着**理论：**离 SM 越远，理论越像广告。** 出处：Jia 2018, Fig. 3.11。
