# WorldStream: Streaming Interactive 3D Worlds with Hierarchical Planning and Persistent State

## TL;DR

**开源世界要同时满足三件互相拉扯的事：无限延伸、听得懂人话、回去还在。** 前两类系统各解决一半——世界模型（MG4.0 / UniWorld 系）能实时出画面，但状态存在帧与隐变量里，**没有"地点标识"**，卸载即失忆；程序化/代码驱动系统（InfiniDream 系）物件可寻址可编辑，但**在开局前就把场景编译完了**，既不决定"下一块该准备哪儿"，也不决定"卸载后什么该留下"。

本文的答案是**把"决策"和"实现"彻底分开，中间只留一份记录**：

- **规划（模型）**：Macro 定区域结构（聚落梯度、生态、交通走廊、水系），Micro 把区域契约特化成瓦片语义；每个字段输出"首选值 + 一个分布"，再由**有界联合求解**挑出同时满足地形/区域契约/邻接承诺的组合。
- **实现（确定性代码）**：接受后的计划是一份**可执行语义规格**，由本地代码编译成地形、道路、聚落、植被、实体——模型不碰顶点。
- **流式（调度）**：两个前沿——语义前沿跑到移动方向前面，实现前沿只编译马上要用的；身后的几何**释放，记录不释放**。
- **持久记录**：$R_i=(G_i,M_i,B_i,O_i,U_i,\rho_i,V_i)$（地理证据 / 计划 / 边界承诺 / 对象状态 / 用户编辑 / 修订号 / 生成器版本），$X_i=\mathrm{Compile}(R_i)$。**几何是可再生资源，记录才是资产。**

四组定量：

| 机制 | 数字 |
|---|---|
| 联合求解 vs 独立取最大概率 | **37% → 100%** 的计划可执行（×2.70）；独立选择让 **63%** 的计划违反至少一条硬约束 |
| 有没有"邻接上下文" | 无 Micro 邻接 → **2,686 栋建筑**（有邻接 250 栋，**10.7× 过度建造**），边界跳变 0.361 vs 0.089 |
| 方向性预取（4 km 路线 / 100 次回放） | 总等待压到 **3.52 s** |
| 本地编译优化 | 密林 10.78 s → **3.32 s**（3.24×）；进程化吞吐 0.234 → 0.464 tiles/s（1.99×） |

> 一句话对读者：**这份论文最值钱的不是"能生成世界"，而是"分头做"的三个前提条件**——共享边界记录（空间）、与调度无关的计划键（顺序）、修订戳（时间）。缺任何一个，异步生成就会长出"每块地各建各的、边界对不上"的经典灾难。你项目的 World Partition + PCG 也在同一张考卷上。

## Problem

论文把三条要求写得很清楚，而且指出它们**分别属于三种不同的系统属性**：

> "extent is a scheduling property, grounded change is a representation property, and reproducibility is a property of what the system stores."

1. **延伸**：世界必须能长到任何预设地图之外，且**每帧成本不随已探索面积增长**。
2. **可作用**：开放语言要能落在"当前存在的实体与地形"上，也要能作用于"还没生成的区域"。
3. **可复现**：卸载过的地点回来时要**连同编辑一起**复原。

现有的两条路各缺一块：

- **学习式世界模型**（Genie / Matrix-Game / UniWorld / LiveAct）：响应性好，一致性窗口在变长，但状态是帧与隐变量——**没有地点标识，没有可改对象**；释放后只能重合成，不能"把上次砍掉的那棵树保持砍掉"。
- **程序化/代码驱动系统**（InfiniDream / Scene-Designer / Co-DSL）：物件可寻址、可编辑，但生成成本付在开局之前、场景固定；**既不决定下一块准备哪儿，也不决定卸载后留什么**。

**它的历史位置**：它既不是"世界模型"也不是"PCG"，而是**把两者接在一根轴上的调度架构**。用库内的话说：MG4.0 是"规则可执行"，InfiniDream 是"AST 可编辑"，本文是"**计划可执行 + 状态可持久 + 工作可按需**"——三者的差别不在生成质量，在**模型输出的是什么**。

## Core Idea

**把"世界"拆成三层，每层有自己的单位与生命周期：**

| 层 | 单位 | 谁生产 | 生命周期 |
|---|---|---|---|
| 语义（这块地是什么） | tile plan $M_i$ | 大模型（Macro/Micro） | 永久（进记录） |
| 几何（长什么样） | 编译产物 $X_i$ | 确定性本地代码 | **临时**（可丢可重建） |
| 交互（谁动过它） | 编辑 $U_i$ + 修订 $\rho_i$ | 语言动作 → 提交规则 | 永久（进记录） |

**关键洞察**：这三层的"贵"完全不同——语义贵在模型推理，几何贵在编译算力，交互贵在**一致性**。所以它们必须**分开预算、分开调度**，而不是像"一次性生成整张地图"那样捆在一起。

## Technical Approach

### 1) 分层规划：Macro 定结构，Micro 定语义

$$M_r=\mathcal P_M(G_r,N_r),\qquad m_i=\mathcal P_\mu(g_i,M_r,N_i)$$

$G_r$ / $g_i$ 是区域级与瓦片级地理证据（高程、坡度、水系、地表），$N_r$ / $N_i$ 是两级的"已接受邻域状态"。Micro 的输出是四元组 $m_i=(Z_i,C_i,A_i,\Theta_i)$：语义分区、边界连接、设施与实体锚点、生成器参数——**这就是给本地代码的接口**。

两级的失败模式是**互补**的（消融图 7 直接展示）：

- **只有 Micro（无 Macro）**：地形兼容，但**永远长不出城市**——每块地都"合理"，整体没有区域意图。
- **只有 Macro（无 Micro 邻接）**：中心与主干道在，但**反复过度建造**（2,686 栋 vs 250 栋），且出现城市/非城市的硬切边（边界跳变 0.361 vs 0.089）。

### 2) 有界联合求解：为什么不能"每个字段取最大概率"

决策模型的每个字段返回"首选值 + 分布"。直觉做法是逐字段取 argmax——**实测 63% 的组合违反至少一条硬约束**（地形不可建、水系冲突、Macro 角色不符、邻接不接）。原因是这些字段**空间耦合**：密住宅要占可建地、退水线要跟实测岸线、用地等级要与 Macro 角色和邻居一致。

联合求解在有界可行集 $\mathcal F$ 上最大化

$$z^\star=\arg\max_{z\in\mathcal F}\Big[\sum_q\log p_q(z_q)+R(z,N_i)\Big]$$

概率项保语义偏好，$R$ 保内部与跨瓦片的平滑过渡，**$\mathcal F$ 的成员资格就是"可执行"的证明**。结果：同样 100 组模型分布，独立选择 37% 可执行，联合求解 **100%**（各约束的单点通过率 ×1.14 ~ ×1.82，整体 ×2.70）。

### 3) 两个前沿：语义跑在前面，几何只做眼前

- **需求三圈**：必做 $R$（当前邻域）、优先 $P$（可见与近未来）、推测 $G$（沿速度方向与相机朝向的预测窗口）。
- **两个预算**：规划预算 $K_p$、建造预算 $K_c\le K_p$；两个视界 $H_p\ge H_c$。于是 $C\subseteq Q$、$|Q|\le K_p$、$|C|\le K_c$——**每一级都有显式并发上界，且"编译一定消费一个已接受的计划"**。
- **方向性预取的价值**：按"预测进入时间"排序，于是**两秒后要穿过的瓦片排在身后更近的瓦片前面**——把预算花在"将要到达"而不是"已经离开"。4 km 路线 100 次回放，总等待 **3.52 s**。
- **自适应视界**：按最近的"派发到完成"时间自动拉长/缩短视界——准备变慢时提前更多。

### 4) 三个一致性机制（这一节最该抄）

异步生成必然遇到"到达顺序不同 → 结果不同"。本文用**三条记录级机制**把"什么时候到"从结果里彻底去掉：

| 机制 | 解决什么 | 具体做法 |
|---|---|---|
| **共享边界记录** | 空间一致 | 相邻两块读**同一条**边界记录（规范道路端口、边缘高程、生态过渡），各自把几何路由到它 |
| **与调度无关的计划键** | 顺序一致 | 计划以 `(瓦片身份, 地理证据, Macro 契约, 邻居承诺, 编辑, 生成器版本)` 为键——预取请求、窗口内请求、重访共享同一结果 |
| **修订戳** | 时间一致 | 每个后台任务带源修订号；安装时只接受"源修订 == 当前记录"的结果，从而不覆盖用户刚提交的编辑 |

第三点尤其重要：它是**乐观并发**（cite 到数据库的乐观并发控制），而不是加锁。语言编辑与后台编译可以同时跑，靠"版本不匹配就丢弃"来保证"用户的最后一次编辑不会被旧结果覆盖"。

### 5) 记录与生命周期

$$R_i=(G_i,M_i,B_i,O_i,U_i,\rho_i,V_i),\qquad X_i=\mathrm{Compile}(R_i)$$

- **驱逐只删 $X_i$**，规划与编辑产生新修订的 $R_i$；
- **唯一/可交互对象**（NPC、地标、用户可寻址物）带显式身份与可变状态；**稠密程序化内容**只留"计划 + 参数 + 掩码 + 种子 + 生成器版本"；
- **一次编辑会把受影响对象"提升"为显式记录**——于是"砍掉一棵树"只需存那棵树，周围森林仍是参数化的。**持久存储的大小 ∝ 可寻址 + 被修改的状态，而不是 ∝ 世界大小**。

## Key Contribution

1. **双前沿流式**：把"语义准备"与"几何准备"分成两个不同长度、不同预算的前沿，使"世界无限延伸"与"每帧成本有界"能同时成立。
2. **可执行的计划**：模型输出的是**带分布的决策**，经联合求解得到**可证明可执行**的语义规格——"模型不碰顶点"是这一条的直接推论。
3. **带修订的世界记录**：把"身份 / 可变状态 / 用户编辑 / 边界承诺"从几何里剥出来，使"卸载—重访"变成重编译而不是重生成。
4. **一套可复用的异步一致性三件套**（边界记录 / 计划键 / 修订戳）。

## Why It Works

- **确定性编译器把"可复现"变成了免费的**：只要记录在、生成器版本在，重编译就是确定的。这一条让"释放几何"不再有风险。
- **预算与需求解耦**：需求由运动预测给（随时间变），预算由 $K_p,K_c$ 给（常数）——于是"探索面积增长"不改变每帧工作量。
- **联合求解比"更好的模型"更便宜**：模型分布不变，只换分辨规则，可执行率 37%→100%。**这是"解码策略 > 模型能力"的一个干净样本**，与 RADIANT 的"换单位 > 调额度"、GaussianSpline 的"换段位置 > 加段数"是同一族结论。

## Limitations

- **词汇表有限**（bounded generation vocabulary）+ 资产是低模程序化：视觉保真度离"能上线的开放世界"还有距离，论文自己把它列为未来工作（接"流式视觉解码器"或"更丰富的显式生成器"）。
- **记录会累积**：长时程世界需要"累积记录的存储策略"，论文明确说这是未解问题（只做了"按可寻址/被修改状态计费"的界）。
- **邻域外的动态 actor 没有模拟策略**——NPC 只在活跃邻域内更新。
- **评测口径偏窄**：规划消融**每个变体只跑一次**（不估模型采样方差）；交互基准只测"语言→正确操作"（80 条双语请求，95.0%），**不含完整的"编辑—驱逐—重访"闭环**；预取回放测的是"后端瓦片就绪"，**排除了浏览器安装**。
- **重建依赖生成器版本兼容**：换一版生成器，旧记录可能编译出不同几何——这是"确定性"最脆弱的一环（论文用 $V_i$ 记录版本，但没有给迁移策略）。
- **规划质量依赖地理证据的质量**：curated geographic rules，不是"从真实世界学出来的地形"。

## Game Development Relevance

- **这就是开放世界的"三本账"**：语义账（这块地是什么）、几何账（编译出来多大）、交互账（谁动过）。项目里常见的事故是**把三本账记在一本上**——例如"玩家改过的场景存进关卡文件"，于是改动一旦跨过流式边界就丢。
- **对 World Partition 的直接对照**：UE 的 Data Layer / Level Instance 提供"加载/卸载"，但**"卸载后复原编辑"**需要你自己设计记录（World Partition 只保存关卡资产，不保存"玩家在这个格子里砍了哪棵树"）。本文的 $R_i$ + 修订戳是一个可直接照抄的 schema。
- **对 PCG 的对照**：UE PCG Graph 是"确定性生成"，天然支持"重跑即复原"；但它**没有"边界承诺"**——两块 graph 各自生成时，接缝处的道路/植被会对不上。本文的"共享边界记录"正是补这一刀。
- **"模型只做决策"这条在你项目里也成立**：凡是让模型输出坐标/顶点的地方，最后都会被"不可复现"咬一口；输出"语义 + 参数 + 种子"则不会。
- **成本口径**：编译 2.1 s/瓦片（均值）意味着"提前 2 秒预取"是硬要求——这与"玩家移动速度 × 视距"直接挂钩，是可写进性能预算的一条。

## Unreal Engine Relevance

- **可借的架构**：World Partition（分块与流式）+ PCG（确定性生成）+ 一份外部"世界记录"（JSON/SQLite）——三者拼起来就是本文的骨架。UE 缺的正是那份记录。
- **可借的调度**：两个前沿（语义/几何）+ 两个预算（$K_p,K_c$）+ 按"预测进入时间"排序——这套可以直接写成 World Partition 的自定义 Source 优先级。
- **可借的一致性**：`边界承诺` ≈ UE 的 Landscape 边缘匹配 + 手动拼花；`修订戳` ≈ 版本化的 Actor 状态（UE 的 SaveGame 可以做，但需要按 tile 分片）。
- **不可直接搬**：本文用 Three.js + 三个编译进程；UE 的编译在编辑器/烘焙阶段，运行时不可能"编译瓦片"——除非把"编译"降级为"实例化预制体 + 参数化摆放"。
