# VDB（Museth 2013）

## TL;DR

**稀疏体数据有个三难：稀疏、随机访问快、拓扑能改——在此之前，你最多拿两个。**

- 八叉树：稀疏 ✅、能改 ✅、快 ❌（深，且每一步都在追指针）；
- DT-Grid / H-RLE：稀疏 ✅✅、快 🟡（必须按序访问）、能改 🟡（重构代价大）；
- 哈希表：稀疏 ✅、快 ✅、**丢掉空间相干性**（模拟最需要的东西）；
- 窄带专用结构：快 ✅，但**限制拓扑**（必须流形、必须闭、必须窄带）。

VDB 三个全拿，办法只有一句话：**把树做浅、做宽，并且让每个节点带两张位掩码。**

代价也一句话：**比最紧凑的表示（DT-Grid）多吃不到 2 倍内存。**

## Problem

稠密网格唯一的毛病是致命的：**内存随包围盒体积增长，而不是随"有内容的地方"增长。**

一个 7897×1504×5774 的包围盒里放 2.28 亿个活跃体素（占有率的 0.04%），稠密表示要 **1/4 TB**，VDB 要 **1 GB**——**250 倍**。

但"省内存"这件事早就有人做了。真正的问题是**省了内存之后还能不能干活**：

| 需求 | 谁需要它 | 谁破坏它 |
|---|---|---|
| 每帧 `O(1)` 随机读一个坐标 | 半拉格朗日 advect、粒子推进、碰撞查询 | 按序存储（DT-Grid/H-RLE） |
| 按 stencil 顺序扫一遍 | 有限差分、WENO、reinitialization | 指针追逐（八叉树） |
| 拓扑随时变（窄带跟着界面走） | level set、火焰、烟、融解 | 只读结构、哈希表重建 |
| 空间相干性 | 缓存、预取、SIMD | 哈希散列 |
| 不设包围盒上限 | 任何有大场景的资产 | 稠密 DAT |

**这五条互相打架，而模拟要全部五条。** 这就是 VDB 要解的问题。

## Core Idea

### 一、树要浅而宽，形状要照着 CPU 缓存长

这是全文最好的一句话，作者自己点出来了：

> VDB 的 root ≈ 主存，internal nodes ≈ L3/L2，leaf ≈ L1。

CPU 的缓存层级是：**一个大的、可动态调整的顶层（主存）+ 少数几级越来越小、越来越快的固定缓存**。VDB 是同一个形状：

| 层 | 大小 | 数量 | 类比 |
|---|---|---|---|
| Root | 无界，哈希/线性表 | 极少（通常几十个） | 主存（可增长） |
| Internal（上层） | 32³ 或 64³ 跨度 | 每个 root 下几百 | L3 |
| Internal（下层） | 16³ 跨度 | 成千 | L2 |
| Leaf | 8³ = 512 体素 | 上百万 | L1 |

**八叉树的错误不是"树"，是"每层只分 2 叉"**——一个 262144³ 的域，八叉树要 18 层，每次访问 18 次指针跳；VDB 用 [6,5,4,3] 只要 4 层，**每次跳覆盖的体素数从 2 涨到 4096**。

**"跳的成本"被"每次跳覆盖的体素数"摊薄了。** 这是全部设计的算术基础。

### 二、一张位掩码，五个用途

每个节点里有两张位掩码：

- **`mChildMask`**：哪些子节点存在（拓扑的上层编码）
- **`mValueMask`**：哪些体素是 active（拓扑的下层编码）

作者说他们是**第一个把这东西同时用于五件事**的：

1. **层级拓扑编码** —— "存在性"变成 1 bit；
2. **快速顺序迭代器** —— 遍历活跃体素 = 遍历置位的 bit；
3. **无损压缩** —— 只有 active 的体素才需要存值；
4. **布尔运算** —— CSG 的并/交/差 = 位与/位或，**整块做，不逐体素**；
5. **拓扑形态学** —— dilation/erosion 也是位运算。

> **这一条是全文真正的核心。** 不是因为位运算快，是因为**"哪些存在"这件事被压缩成了 1 bit/体素/层之后，拓扑操作就从"改数据"变成了"改位图"**——而位图可以整块处理，不需要 for 循环。**今天 Sifakis 2026 的整篇论文，就是把这五件事搬到 GPU 上做。**

### 三、值可以住在任何层，但不同层不重叠

VDB 允许在 internal node 上存一个 **tile value**（一整块用同一个值）。作者特意强调：

> 这些多层值**在索引空间上互不重叠**。所以 VDB 不同于 brickmap / mipmap——后者在同一个索引空间里表示多个 LOD。

**这个区分很实用**：VDB 不是多分辨率结构，是**"同一分辨率下，空的地方用一个常数代替"**。想多分辨率，得自己搭金字塔。

### 四、accessor：让"跳"变成"记得上次跳到哪"

随机访问的代价是"从根走到叶"。VDB 的 accessor 是一个**软件缓存**：记住上次访问的叶节点，若下一次还在同一个叶里，**完全跳过遍历**。

更关键的是"**反向遍历**"：树深固定 + 分支因子固定 ⇒ 从缓存的叶可以**向上算出**任意祖先的地址，不必从根往下走。于是：

> **空间相干访问的摊还复杂度与树深无关。**

**"固定深度"这个设计决定的真正目的不是省内存，是让反向遍历成立。** 这是我认为这篇最容易被读漏的一点。

## Technical Approach

### 节点结构

- **Leaf**：8³ = 512 个体素的值缓冲（**大小可变**——可以压缩、可以位量化、可以在 out-of-core 下只存一个文件偏移）+ `mValueMask` + `mFlags`（含 origin）。
  - **leaf 是自包含的**：把 origin 编进 flags，不需要引用父节点。省一次指针跳，也简化了坐标推导。
- **Internal**：`mInternalDAT`（稠密直接访问表，把所有子指针/子值放在一个连续数组里）+ `mChildMask`。**DAT 是"稠密"的**——这就是"宽度"的代价：2^(3·LOG2DIM) 个槽位，每个槽要么是子指针，要么是一个 tile 值。
- **Root**：稀疏、可动态调整（哈希表或线性表）。**只有它需要增长。**

### 配置空间：为什么是 [6,5,4,3]

配置写成 `[LOG2DIM_0, LOG2DIM_1, ...]`，每层节点侧长 = 2^LOG2DIM。三个约束互相拉扯：

1. **树要深一点** → 域大、顶层 DAT 小；
2. **树要浅一点** → 跳数少、访问快；
3. **叶节点要小** → 稀疏数据的浪费少（8³ 的叶在 1% 占用时浪费 99%）；
4. **叶节点要大** → 缓存友好、每跳覆盖更多。

实测结论：**`[6,5,4,3]` 最好**（4 层：64³ / 32³ / 16³ / 8³，可用侧长 $2^{18}$）。

反例很有说服力：`[10,3]` 与 `[6,4,3]` **可用分辨率完全相同**，但 `[10,3]` 的顶层 DAT 是 $1024^3$ 个槽——**内存差几个数量级**。**同分辨率、不同分层，内存可以差到不可用。** 这是"树形配置"这件事唯一必须记住的一条。

### 三个"数据结构的副产品"

1. **拓扑感知的无损压缩**：只存 active 体素；未用满的叶节点可以裁掉尾部。可叠加位量化（16-bit / 8-bit）+ 标准压缩。
2. **Out-of-core**：值缓冲可以放到磁盘，**内存里只留拓扑**；渲染时按块加载。这一条在 2013 年是生产刚需（云的分辨率 15000×900×500）。
3. **免 bucket sort 的网格转 level set**：以前要先按 Morton 序排一遍（时间 + 内存都贵），VDB 可以**按乱序插入**——因为插入本身就是分摊 O(1)。

### 算法：dilation / erosion / CSG / flood-fill

全部建立在"整块位运算"上：

- **dilation**：对每个叶，用位掩码扩 26 邻域（跨叶的部分交给邻居的 mask）；
- **CSG**：两棵树的并/交/差 = 逐节点的 mask 布尔 + tile 值合并，**空节点直接剪枝**；
- **flood-fill**：从种子开始按 tile 扩展，tile 级判断"整块是否全在内/全在外"，**遇到界面才细到体素**。

**共同点：能整块判的绝不到体素。** 这就是"宽节点"的回报。

## Key Contribution

1. **一个同时满足"稀疏 / 随机访问 / 动态拓扑"的数据结构**，且是第一个（作者原话：`to the best of our knowledge, VDB is the first to embody all`）。
2. **位掩码的五重用法**：拓扑、迭代、压缩、布尔、形态学共用同一份 1 bit/体素。
3. **"树形照缓存长"的设计语言**：浅而宽 + 固定深度 + 反向遍历。
4. **工程化的完整性**：压缩、out-of-core、无 bucket sort 的转换、生产验证。

## Why It Works

### 内存账：为什么"多吃 <2 倍"是划算的

| | VDB | DT-Grid |
|---|---|---|
| 内存 | 1× | **0.5–0.6×**（更省） |
| 平流（advection） | **4–35×** 快 | 1× |
| 空间相干查找 | **>10×** 快 | 1× |
| 写入 | **3–4×** 快 | 1× |
| 形态学 dilation | **7×** 快 | 1× |
| CSG | **>100×** 快 | 1× |

**用不到两倍的内存，换 4 到 100 倍的算力。** 这个交换在 2013 年的工作站上（48 GB 内存）是毫无疑问的；在今天的 GPU 上更是（显存更贵，但带宽更贵）。

> **这是"计价单位"的一个经典样本**：VDB 不是在"省内存"这条轴上竞争，是**把内存换成了"能随机访问"和"能改"**。选错了计价单位，就会得出"DT-Grid 更好"的结论。

### 为什么位掩码能同时干五件事

因为这五件事问的都是同一个问题：**"这个位置存在吗？"**

- 拓扑编码 = 存这个问题；
- 顺序迭代 = 按答案走；
- 压缩 = 答案是否，就不用存值；
- 布尔运算 = 两个答案做逻辑；
- 形态学 = 答案在邻域上做卷积。

**一旦你把"存在性"抽出来单独存，剩下的全部操作都变成对它的操作。** 这是数据表示设计里最干净的一次"提取公因式"。

### 为什么"浅"这件事不能靠"大叶节点"硬凑

`[10,3]` 的教训：把树压到 2 层，叶还是 8³，那么上层必须是 $1024^3$ 的稠密 DAT——**内存立刻爆炸**。

**"浅"必须靠"每层多分叉"来实现，而每层多分叉的代价是"该层的 DAT 变大"。** 这两者的乘积被树深约束死，所以存在一个最优深度。**这不是调参，是一道有解的优化题。**

## Limitations

### 论文自陈

- **比 DT-Grid 多吃 <2× 内存**（作者主动写进结论，没有藏）。
- **指针 + 堆分配 ⇒ GPU 不友好**。这一条当时只是"未来工作"级别的备注，**八年后成了 NanoVDB 存在的全部理由**。
- **配置（树深 / 分支因子）是编译期的**，选错了要重编。运行时不可调。
- **只有拓扑能整块处理；值不行**。值的读写仍然逐体素（这是 2026 那篇 `inject` 要解决的问题）。
- **作者自己注明**：文章投稿半年后 OpenVDB 才开源，所以**文中少数实现细节与 OpenVDB 不完全一致**。

### 十三年后的回看（我的判断，非论文）

- **"动态"这个词在 2013 年是"体素粒度可增删"**。到了 2026 年，同样的问题被重新问了一遍，答案是"**批量同步**"——因为 GPU 上"体素粒度"这件事本身就是错的。**同一个词，两代人的含义不同。**
- **最深远的遗产不是数据结构，是文件格式。** VDB 成为 DCC 的事实标准（Houdini / Cycles / Arnold / V-Ray / RenderMan），这件事的复利远大于论文里的任何倍数。

## Game Development Relevance

**为什么一个 2013 年的数据结构页，值得放在游戏研发库里**：

1. **它是"体积"这件事的存储层标准。** 你在 Houdini 里做的烟、火、云、爆炸缓存，落到磁盘上就是 `.vdb`。不理解树与位掩码，就理解不了"为什么改分辨率会让缓存重算"、"为什么 8³ 叶节点是最小浪费单位"、"为什么 tile value 能让空区域几乎免费"。
2. **它是"数据结构的形状决定能力边界"的最干净样本。** 游戏里每个自建系统都会遇到同一类问题：**在"省内存"和"能随机访问"之间，你选了哪一边，就决定了后面三年能做什么。**
3. **它是 2026 那篇的前置条件。** 今天读 [[2026-11-10-Sifakis — Dynamic GPU Sparse Grids and Voxel-sequential Processing in NanoVDB|Sifakis 2026]] 时，所有术语（root tile / internal / leaf / childMask / valueMask / accessor / DAT）都来自这里。**不读这篇，那篇读起来会像一本只讲优化的工程报告。**

**不适合的游戏场景**：方块体素地形（dense chunk + 面剔除才是对的）、静态网格的碰撞（用 BVH）、只需要"有/没有"的占据查询（用哈希）。

## Unreal Engine Relevance

- **没有原生集成**，但工作流上有两条真实的路径：
  1. **Houdini → UE**：VDB 是中间格式；理解 tile value 与叶节点大小，直接决定了"为什么同样的烟，按 32³ 切块导入会比按 8³ 快很多"。
  2. **自建体积系统**：如果要做体积雾 / SDF GI / 破坏的内部距离场，VDB 的三条设计（浅宽树、位掩码、tile value）可以照抄——**尤其是 tile value：它让"空的地方"几乎不要钱**。
- **不该抄的部分**：指针 + 堆。在 GPU 上那是 2021 年就被否掉的路线。

## Relationships

### Based On

- **B+ 树**（Bayer & McCreight 1972）：作者明说 VDB 是"B+ 树在稀疏体网格上的一个特定优化"。差别有三：VDB 在**所有层**都存值（B+ 树只在叶存记录）；不用 key（坐标直接算地址）；**常数时间随机访问**（B+ 树是对数）。
- **DT-Grid / H-RLE**（Nielsen & Museth 2006；Houston et al. 2006）：主要的对照基线，也是"最省内存"这条轴的守擂者。

### Extends

- **DB-Grid → DB+Grid**：作者自己的两代前身。DB+Grid 已经是"DB-Grid + B+Tree"，本篇是把它的**节点尺寸、位掩码语义、accessor 反向遍历**讲成一套完整设计。

### Related

- **[[Sparse Volumetric Representation]]**（今日新建）：本篇是这条线的**分水岭节点**——它之前是"各种专用结构"，它之后是"VDB 与其 GPU 变体"。
- **[[Fluid Simulation]]**：窄带 level set 是它的主应用；dilate → advect → reinit → prune 的四步循环里，前三步全部依赖本篇的拓扑能力。
- **[[Participating Media]]**：体积渲染读的就是这种网格；HDDA 让它不必转成稠密。
- **[[GPU Architecture]]**：本篇是"CPU 缓存层级"的直接类比；它的失败面（指针 + 堆）也正是 GPU 架构的反面。

### Contrasts

- **与八叉树**：**深而窄 vs 浅而宽**。八叉树每层 2 叉，跳数 $O(\log_2 N)$；VDB 每层 8–64 叉，跳数固定 3–4。**差别不在"是不是树"，在"每次跳覆盖多少"**。
- **与哈希表**：哈希给 O(1)，但**毁掉空间相干性**——而模拟的整个性能模型建立在相干性上（缓存、预取、SIMT）。
- **与 brickmap / mipmap**：那两者在**同一索引空间**表示多个 LOD；VDB 的多层值**互不重叠**，只是"空的地方用常数代替"。**别把 VDB 当多分辨率结构用。**

### Followed By

## Learning Value

**这一篇的价值不在"知道 VDB 是什么"，在三个可迁移的设计判断：**

1. **"浅而宽"优于"深而窄"，因为成本按"跳数 ÷ 每跳覆盖"算。** 这个式子可以套在任何层级结构上（场景图、BVH、骨骼层级、文件目录）。
2. **把"存在性"抽出来单独存，剩下的操作全部变成对它的操作。** 位掩码五用是这句话的极端样本；实践里"单独的 occupancy 位图 / dirty flag 表"是同一个动作。
3. **"多吃 2 倍内存换 100 倍算力"要先说清计价单位。** 说"VDB 比 DT-Grid 费内存"是对的，但漏掉了它买到的东西。
